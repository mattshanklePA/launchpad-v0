# LaunchPad — Architecture & Environment Guide

**Audience:** an engineer or collaborator joining the project.
**Goal:** understand the lay of the land fast — what the system is, how it is built, where things live, how to run it, and where customization is meant to happen.

**Last updated:** 2026-06-11 · **Branch:** `USPTO-launchpad`

---

## 1. What LaunchPad is

LaunchPad is a web application for intake and governance of AI use cases in a government setting. People submit AI ideas through a guided, plain-language wizard. An AI assistant vets and structures each idea. Reviewers and leaders track everything through a pipeline and compare candidates in a Decision Center to decide what to fund.

It is currently a working **prototype**, not an authorized production system.

---

## 2. Tech stack

- **Framework:** Next.js 14 (App Router) on React 19, TypeScript.
- **UI:** Tailwind CSS, Radix UI primitives via shadcn/ui, lucide-react icons, framer-motion, sonner (toasts), recharts (charts).
- **AI:** Vercel AI SDK (`ai` v5) with the Anthropic provider (`@ai-sdk/anthropic`). Structured outputs via `generateObject` + zod schemas.
- **Data:** Supabase (hosted Postgres) via `@supabase/supabase-js`.
- **Forms:** react-hook-form + zod.
- **PDF export:** jspdf / jspdf-autotable.
- **Hosting:** Vercel (app) + Supabase (database).
- **Package manager:** pnpm.

---

## 3. High-level architecture (request flow)

```
Browser (React client components)
  -> Next.js App Router (server actions + API route handlers in app/api)
    -> lib/* domain logic
      -> Supabase Postgres (server-side, service-role)  and  Anthropic (server-side)
```

**Key rule:** the browser never talks to Supabase directly. All data access goes through server-side API routes / server actions using the service-role client. This keeps DB credentials and access policy on the server (see `lib/supabaseClient.ts`).

## 5. Data model & persistence

- Submissions are stored in Supabase Postgres. A row carries structured columns plus a `form_data` JSON blob holding the full wizard payload, review status, and comments.
- Access pattern: API routes call `lib/submissions.ts` helpers — `saveSubmission` (new), `patchSubmissionFormData` (update in place), `setSubmissionStatus`.
- `lib/submissions.ts` keeps its public API but now delegates to the **SubmissionStore** port via `getStore()` (`lib/submissionStore.ts`). The default adapter is `lib/adapters/default/supabaseStore.ts`. Callers and signatures are unchanged; to run against an agency database, swap the store in `lib/submissionStore.ts`.
- Status lives in both a `status` column and `form_data.reviewStatus`; comments live in `form_data.comments` (no separate comments table). Keep column and JSON in sync via the helpers.
- **Migrating a `form_data` field's shape** ([issue #116](https://github.com/mattshanklePA/launchpad-v0/issues/116)) doesn't need a DB backfill — `form_data` is unstructured JSON, so a shape change is normalized at the read boundary instead. `lib/formDataMigrations.ts`'s `migrateFormData()` is applied once, in `supabaseStore.ts`'s `getSubmissions()`, so every consumer of `Submission.formData` (admin tables, exports, dashboard metrics) sees the current shape regardless of when the underlying row was written. Precedent: the `isWithheld` four-way field replacing the two-way `publicIndicator` flag — legacy `"public"` maps to `"no"`, legacy `"excluded"` maps to `"other"` (the old flag never recorded *why*, so "Other" is the only faithful mapping for data that predates the reason).
- Two Supabase clients (`lib/supabaseClient.ts`):
  - `getSupabaseAdmin()` — service_role key, bypasses RLS, **server-only**. Never import into client code.
  - `getSupabaseAnon()` — publishable key, browser-safe, **currently unused** (kept for future realtime).
- Migrations in `db/migrations/`: review workflow, demo status fixes, demo examples, users & assignees. Tenant-specific migrations live under `db/migrations/<tenant>/` (e.g. `db/migrations/doc/`).

### Org hierarchy: Department -> Bureau -> Office (DoC)

The DoC tenant models a three-tier org taxonomy:

- **Department** — the whole tenant (Commerce). The Office of the Secretary (`businessUnit === "os"`) and a department-level viewer with no `businessUnit` (e.g. the seeded department admin) see every submission — the only two cross-bureau (roll-up) views.
- **Bureau** — `submissions.business_unit` / `users.business_unit`, driven by `getTenant().unit.options` (e.g. `census`, `noaa`). This tier existed before the office work; roll-up is `components/admin/bureau-rollup.tsx`.
- **Office** — `submissions.office` / `users.office` (added in `db/migrations/doc/0001_office_hierarchy.sql`), an optional sub-level under a bureau. Only bureaus that declare `offices` on their `UnitOption` in `lib/tenant/doc.ts` (currently Census, ITA, NOAA) show an office dropdown in the wizard (`components/steps/step-1-submitter-info.tsx`) or an office drill-down under their roll-up row (`components/admin/office-rollup.tsx`, aggregation in `lib/officeRollup.ts`). Bureaus without offices behave exactly as before — `offices` is optional so USPTO and DoW are unaffected.
- **Admin assignment** — an admin sets a reviewer's bureau and office from `components/admin/user-management.tsx`. The bureau dropdown reads options from `getTenant().unit.options` (tenant-aware, no hardcoded USPTO list); a dependent office dropdown appears only when the selected bureau declares `offices`, and resets whenever the bureau changes. Both fields persist via the existing `PATCH /api/users/:id` (no schema/API changes — office was already plumbed end-to-end). **A reviewer must log out and back in for a new bureau/office assignment to take effect** — `office`/`business_unit` are read onto the session at login (`lib/auth.ts`), not re-read live, so `visibleSubmissions` roll-down scoping reflects the change only after re-authentication.

**Roll-down visibility (`visibleSubmissions` in `lib/reviewWorkflow.ts`)** mirrors this, and hard-limits every bureau-assigned viewer to their own bureau: a submitter sees only their own submissions; a reviewer *or admin* with a non-`os` `businessUnit` sees only that bureau (narrowed further to `office` when set) — an admin's bureau assignment rolls down exactly like a reviewer's, so e.g. a NOAA admin never sees BEA's or Census's submissions. The Office of the Secretary (`businessUnit === "os"`) and a viewer with no `businessUnit` at all (department admin, or a reviewer with no unit) keep the roll-up and see everything. Every admin/reviewer surface routes through this one function so nothing bypasses the scope: the Command Center dashboard (`getDashboardScope`/`scopedSubmissions`, see "Command Center landing dashboard" below, mirror this same rule), the bureau roll-up (`components/admin/bureau-rollup.tsx`, scoped via the `submissions` prop its caller passes in), Decision Center (`components/admin/decision-center.tsx`, which now takes a pre-scoped `submissions` prop rather than fetching unfiltered data itself), the admin dashboard's Overview/Idea Pipeline tabs (`app/admin/page.tsx`, scoped at the point it hydrates its `submissions` state from the cache), and the submission detail page (`components/submissions/submission-detail.tsx`, which re-checks `visibleSubmissions([sub], viewer)` so a direct link to another bureau's submission ID can't bypass the list-level scope; its "similar use cases" cross-bureau duplicate surface is likewise computed only over the viewer's visible set).

**RLS posture:** `0001_office_hierarchy.sql` enables row level security on `submissions` with a policy for the `authenticated` Postgres role that mirrors the *previous* `visibleSubmissions` behavior (admin claim sees all; bureau claim scopes to `business_unit`; office claim further scopes to `office`), keyed on `auth.jwt() -> 'app_metadata'`. The app currently talks to Supabase only via the service_role client (`getSupabaseAdmin()`), which has `BYPASSRLS`, so this policy does not enforce anything today and does not yet reflect the admin bureau roll-down added here — it exists so DB-level scoping is already in place, not as the active security boundary. **`visibleSubmissions` is a client-side filter only, not a security boundary** — the app-level hard limit this section describes is what the DoC demo depends on today. **Follow-up (not done in this PR, tracked separately):** true server-side enforcement requires migrating the app's own auth (`lib/auth.ts`, a custom users table) onto Supabase Auth or another scheme that mints a per-request JWT carrying `role`/`business_unit`/`office` claims — that work depends on the pluggable-auth / SSO effort, at which point the RLS policy above should also be updated to match the admin roll-down (currently it still grants every `admin` claim full access, matching pre-roll-down behavior).

#### Per-bureau strategic priorities (DoC)

A `UnitOption` (`lib/tenant/types.ts`) can optionally declare its own `focusAreas?: FocusArea[]` — a bureau's own strategic priorities, in the same `{ id, label, category, description? }` shape as the tenant-level `TenantConfig.focusAreas`. `lib/tenant/doc.ts` populates this for every DoC bureau (source data + citations in `docs/research/doc-bureau-strategic-priorities.md`); the tenant-level `doc.focusAreas` (the OMB/federal-AI-framework list) remains the department-level fallback. USPTO and DoW `UnitOption`s never declare `focusAreas`, so they are unaffected — additive and optional, same pattern as `offices`.

`lib/strategicFocusAreas.ts` exports `getFocusAreasForUnit(businessUnit?: string | null): FocusArea[]`, the single place that resolves "which priority list applies here": it looks up `businessUnit` in `getTenant().unit.options` and returns that bureau's `focusAreas` when declared and non-empty, otherwise `tenant.focusAreas`. Two call sites use it to score/display against the *submission's own bureau* rather than the department-wide list:

- **Strategic Alignment Scout** (`suggestStrategicAlignment` in `app/actions.ts`) — scopes both the AI prompt's candidate focus-area list and the hallucination-guard validation (`validIds`) to `getFocusAreasForUnit(formData.submitterOffice)`, so a submitter under a bureau is scored against that bureau's mission, not Commerce's. **Not currently wired into the wizard** — issue #162 removed the Strategic Alignment step from idea intake entirely (alignment is filled in during vetting instead); the action and `lib/strategicFocusAreas.ts` are kept as-is, unused by the wizard today, as a starting point for a future vetting-side alignment capture surface (the same pattern issue #161 used for the OMB/M-25-21 fields).
- **Admin OKR cards** (`app/admin/page.tsx`, the `{tenant.okrsLabel}` tab) — a bureau selector (rendered only when at least one bureau declares `focusAreas`, i.e. DoC) lets a viewer scope the OKR card list to a single bureau; the default/unscoped selection shows the department-level list, matching prior behavior for USPTO/DoW where no selector renders at all.

`lib/tenant/index.ts` exports the companion `getOrgNameForUnit(businessUnit?: string | null): string`, resolving "whose name goes in this sentence" the same way: it returns the matched `UnitOption.label` (e.g. "U.S. Census Bureau") only when that option declares `focusAreas` — the same bureau-tier gate as `getFocusAreasForUnit` — and falls back to `tenant.orgName` otherwise. Consumers: the alignment section heading in the PDF export (`lib/pdfGenerator.ts`), and (pre-#162) the now-unused Strategic Alignment Scout action above.

#### Registered tenants

Every tenant is one `lib/tenant/*.ts` file registered in `lib/tenant/index.ts`'s `TENANTS` map and selected at deploy time by `NEXT_PUBLIC_TENANT`. `getTenant()` defaults to `uspto` when the variable is unset, so adding a tenant never moves the default. `ALL_TENANTS` (same module) exposes the registered set for checks that must hold across all of them.

| `NEXT_PUBLIC_TENANT` | Org | Product / assistant | Tier vocabulary (`tierLabels`) | Bureau tier? |
| --- | --- | --- | --- | --- |
| `uspto` | USPTO | LaunchPad / Scout | Agency → Business Unit | no |
| `dow` | Department of War | LaunchPad / Scout | Department → Command | no |
| `doc` | Department of Commerce | Keystone / Plumb | Department → Bureau → Office | yes |
| `es2` | Enterprise Software and Services (Army CPE ES2) | Keystone / Plumb | Enterprise → Program Office → Program | yes |

"Bureau tier?" is `tenantHasBureauTier()` — true when any `unit.options` entry declares its own `focusAreas`, which is what gates sign-off, cross-unit rationalization, and the roll-up views (see "Per-bureau strategic priorities" above). DoC declares it per bureau; ES2 declares it for all five program offices, deliberately, because the demo is built on those surfaces.

**ES2** (`lib/tenant/es2.ts`, ISS-4) is a configured instance of the same product DoC runs — `productName` "Keystone", `assistantName` "Plumb" — not a second product. Its `unit.options` values (`atr`, `hrfm`, `logfin`, `bts`, `cerp`) and AT&R's `offices` values (`acws`, `atis`, `fmsaces`, `digitalmarket`) are load-bearing: the seed data and `db/migrations/es2/0000_es2_base_schema.sql`'s column comments reference them by name. Its labels are verbatim from the organization's published org chart, ampersand and en-dash inconsistencies included. Two optional fields are deliberately unset — `heroImage` (so the hero falls back to `theme.primary` rather than inheriting another org's imagery) and `trlSystemName` (no downstream marketplace an internal submitter files into; TRL still renders without it). Throughout that file the department is the **Department of War / DoW**; a test walks every string in the config asserting none matches `/\bDoD\b/`, while published directive numbers keep their own spelling (`humanReviewCitation` is "Governable / DoDD 3000.09"). A reusable generic commercial baseline that `es2.ts` would extend is the right long-term shape and is deliberately deferred until after the demo.

#### Wizard step copy (tenant-aware)

The admin dashboard fix above (`okrsLabel`) covered the admin surface only; the submission wizard itself had its own hardcoded DoW/DoD copy (org name, strategic-priorities framing, and Feasibility & Security's DoD-specific citations) that leaked onto every tenant, including DoC. That copy now comes from `TenantConfig` (`lib/tenant/types.ts`) instead:

- `orgName` — the org's full name/acronym, still used in PDF-export and reviewer-facing copy. Bare, no leading article; callers add "the" inline where the sentence needs one.
- `dataMaturityFraming` / `modelSourcingGuidance` — originally the Feasibility & Security step's "Data readiness & maturity" subtitle and model-sourcing paragraph; that step no longer exists in the wizard (issue #162 moved it to vetting-only), so these fields are currently unused by any component but kept on `TenantConfig` for a future vetting-side surface.
- `trlSystemName` / `srgCaveat` / `humanReviewCitation` — optional, DoW-only citations (its "Tradewinds" system, the DoD SRG caveat, DoDD 3000.09); same status as the two fields above — unused by the wizard post-#162, kept on `TenantConfig` for vetting-side reuse.
- `lib/steps.ts` exports `getFormSteps(submitterOffice?: string | null)` (not a static array). Pre-#162 this resolved per-tenant `orgName` into the Value and Strategic Alignment steps' title/prompt; both steps are gone from idea intake now, so the step copy is tenant-neutral wording and `submitterOffice` is accepted only for call-site compatibility. Every consumer (`step-wrapper.tsx`, the Review & Submit recap cards, `wizard-nav.tsx`, `progress-bar.tsx`) still calls the function rather than importing a shared constant, in case a future step reintroduces tenant-specific copy.
- `getSubmitterRoleLabels()` (also `lib/steps.ts`) is the single source of truth for the `submitterRole` enum's display labels, resolved from `getTenant().submitterRoles` — reused by the "Submitting as…" pill (`form-container.tsx`), the Review & Submit recap, and the PDF export (`lib/pdfGenerator.ts`) — previously the pill kept its own stale copy of a static map and could show a USPTO-flavored role name regardless of the role actually selected.

#### Submit-wizard dropdown options (tenant-aware, issue #147)

The submit wizard's dropdown *option lists* — not just their labels — used to be hardcoded USPTO copy that leaked into every tenant (a DoC or DoW submitter picking "Patent Examiner" as their target audience, or seeing DoD Impact Levels as the only data-classification choices). Four `TenantConfig` (`lib/tenant/types.ts`) arrays fix this, following the exact pattern `unit.options` already established — a `SelectOption[]` (`{ value, label }`) the active tenant supplies, and the step component just maps over it instead of hardcoding `<SelectItem>`s:

- `submitterRoles` — Step 1 "Role" (`step-1-submitter-info.tsx`).
- `affectedSystems` — Step 2 "Which process, system, or group does this affect?" (`step-3-problem-and-users.tsx`, the idea intake's Business Problem & Opportunity step).
- `targetAudiences` — Step 2 "Primary audience" (`step-3-problem-and-users.tsx`).
- `dataClassifications` — "Data classification / required Impact Level"; DoD Impact Levels for USPTO/DoW (`unclassified`/`cui`/`il5`/`il6`, USPTO's pre-existing default, unchanged), FISMA impact levels for DoC (`fisma_low`/`fisma_moderate`/`fisma_high`). No longer rendered in the wizard as of issue #162 (the Feasibility & Security step it lived on moved to vetting-only) — a reviewer sets it via `components/submissions/governance-capture-panel.tsx` instead.

Values are free strings, not a shared union — `FormData`'s `submitterRole`/`targetAudience`/`impactLevel` fields are plain `string` (same as `submitterOffice`); `affectedBusinessUnits` (issue #163) is the one exception, a `string[]` multi-select over the same `affectedSystems` option list. Each tenant's list can differ from another's entirely. USPTO's four arrays carry today's exact values (guardrail: USPTO renders identically), and both USPTO and DoW reuse the same generic `submitterRoles`/`dataClassifications` lists since those were already tenant-neutral; DoC and DoW get their own `affectedSystems`/`targetAudiences`. A couple of DoC/DoW values were deliberately kept identical to USPTO's (`other`, `product_owner`, `applicant`, `cross_functional`, `it_staff`, `manager`) so the existing DoC/DoW demo seed data (`lib/seedSubmissionsDoc.ts`, `db/migrations/dow/0002_dow_seed.sql`) keeps resolving to a real label instead of falling back to the raw stored value — no data migration needed. The Review & Submit recap's `ENUM_LABELS` (`step-10-review-submit.tsx`) resolves all four option sets' labels the same way it already resolved `unit.options` — `Object.fromEntries(tenant.<field>.map(o => [o.value, o.label]))` — so a stored value from any tenant's list still shows its label there and in the PDF export.

The Review & Submit step's "Route to" options work the same way but reuse an *existing* tenant signal rather than a new array: "Export to Rally" is filtered out of `routeOptions` unless `getTenant().features.rallyExport` is on (USPTO only; DoW/DoC already had this off). The universal/federal-standard option lists (OMB topic area, AI classification, demographic features, public-consultation steps, stage of development, TRL, model sourcing) stay hardcoded — they're federal-standard vocabularies every tenant reports against identically, not org-specific taxonomy.

**ES2-13** extends both of those signals. `JobRole` (`lib/auth.ts`) is now a plain `string`, like the `BusinessUnit` beside it, rather than a USPTO-shaped union, so User Management's job-role dropdown could stop hardcoding one: `jobRoleOptions()` (`components/admin/user-management.tsx`) returns the active tenant's `submitterRoles` with "Not set" prepended — the same list Step 1 offers, so a role reads the same label on both surfaces. USPTO, DoC and DoW keep the same eight values (no stored `job_role` becomes unrepresentable), with `patent_examiner`/`trademark_examiner` now reading "Operations / Staff Officer" / "Analyst" as intake already showed them. `features.rallyExport` also gates the two Rally surfaces that had escaped it — Step 11's "View in Rally" button (`components/steps/step-11-export-tracking.tsx`), the screen every intake ends on, and the "Rally Integration Endpoint" field in Settings → Platform Configuration (`app/admin/page.tsx`) — so a tenant without the integration shows none of it. With tenant roles now assignable, the ES2 user seed populates `job_role` (`db/migrations/es2/0001_es2_users_seed.sql`) for Step 1's pre-fill; `db/migrations/es2/0002_es2_job_roles.sql` brings the already-deployed instance in line and is **run by hand in Supabase**, not by the app.

#### Affected business units, client sponsor, and delivery audience (issue #163)

Three intake fields added to the idea flow at Jonathan's (USPTO) request:

- **`affectedBusinessUnits: string[]`** (`lib/steps.ts`) — replaces the earlier single-value `affectedSystem: string`. Multi-select, rendered as a toggle-pill group (`components/steps/step-3-problem-and-users.tsx`, same pattern as `problemType`) sourced from the tenant's existing `affectedSystems` option list — no new `TenantConfig` array needed, since that list already carries per-tenant, per-bureau option values (see "Submit-wizard dropdown options" above). Required to submit, same as the field it replaces (`lib/submissionReadiness.ts`).
- **`sponsorName` / `sponsorRole` / `sponsorEmail: string`** — optional client-sponsor identification, rendered on Step 1 (Submitter Info, `step-1-submitter-info.tsx`) below the submitter's own fields. Left blank when the submitter is their own sponsor; never required.
- **`deliveryAudience: "internal" | "external" | ""`** — whether the proposed solution is for internal staff or is customer/public-facing, rendered on Step 3 (Proposed Solution, `step-3-solution-benefits.tsx`) via the same `OptionRadioGroup` button-card pattern used for `impactedUsersCount`. Optional; the `internal`/`external` labels already existed in the Review & Submit recap's `ENUM_LABELS` (shared with `securityClassification`), so no new label mapping was needed there.

All three are registered in `lib/fieldRegistry.ts` (togglable via the admin Form Configuration tab, same as any other field) and surfaced in the Review & Submit recap (`STEP_FIELDS`, `step-10-review-submit.tsx`) and the reviewer-side submission detail page (`components/submissions/submission-detail.tsx`'s "Submission" card).

**Migrating `affectedSystem` → `affectedBusinessUnits`** follows the read-boundary pattern established for `isWithheld`/`publicIndicator` (see "Migrating a `form_data` field's shape" above): `lib/formDataMigrations.ts`'s `migrateAffectedBusinessUnits()` wraps a legacy single-string `affectedSystem` value into a one-element array, passes an already-migrated array through unchanged, and returns `[]` when neither field is present — applied inside `migrateFormData()`, so every existing submission (including the seed data in `lib/seedSubmissions.ts`/`lib/seedSubmissionsDoc.ts`, converted to the new array shape directly since seed data is regenerated, not legacy) reads correctly with no DB backfill.

#### Org-tier labels (`tierLabels`, tenant-aware)

The tier *structure* and the tier *vocabulary* are two different things, and only the second one is per-tenant. The structure is fixed and stays in code: `tenantHasBureauTier()` (`lib/tenant/index.ts`), the `submissions.business_unit` / `submissions.office` and `users.business_unit` / `users.office` columns, `FieldLevel`'s `"bureau"` value (`lib/fieldRegistry.ts`), and the `lib/bureauSignoff.ts` / `lib/crossBureauDuplicates.ts` / `lib/officeRollup.ts` modules with their component filenames. None of those names reach a screen, and none of them are tenant-specific.

What *does* reach a screen is the word a user reads for each tier, and that used to be hardcoded Commerce language — literal `"Bureau"` / `"bureaus"` / `"Office"` strings scattered across admin, dashboard, wizard, and landing components, so every non-Commerce tenant read as a Department of Commerce tool. `TenantConfig.tierLabels` (`lib/tenant/types.ts`) moves just that display vocabulary into config, the same way `unit.label`, `okrsLabel`, `productName`, `assistantName`, and the wizard dropdown option lists already work:

```ts
tierLabels: {
  department: string    // top tier, e.g. "Department"
  unit: string          // middle tier, singular, e.g. "Bureau"
  unitPlural: string    // e.g. "Bureaus"
  subUnit: string       // optional third tier, singular, e.g. "Office"
  subUnitPlural: string // e.g. "Offices"
}
```

Every tenant supplies all five (there is no shared default to fall back to, so no org's vocabulary can leak into another's UI): DoC is `Department` / `Bureau` / `Bureaus` / `Office` / `Offices` — chosen so every swapped string resolves back to exactly the text it printed before (with the two approved exceptions noted at the end of this subsection), the guardrail `lib/tenant/tenant.test.ts` pins; USPTO is `Agency` / `Business Unit` / `Business Units`; DoW is `Department` / `Command` / `Commands`. **Tier labels are title case for every tenant**, because they are composed into other strings (`Affected ${unitPlural}`, `{unit} roll-up`) where a half-capitalized label reads as a typo — sentence case on USPTO's is what once produced "Affected Business units". `lib/tenant/tenant.test.ts` pins that convention across every registered tenant (`ALL_TENANTS`), so a newly added tenant is checked automatically. `unit` names the same tier as the tenant's own `unit.label` so the form-field label and the tier noun can't drift, but the two may differ in form: `unit.label` is sentence case (it renders on the wizard's step-1 input — USPTO's is "Business unit"), and DoW's is the slash-joined "Command / organization" whose tier noun drops the slash so it reads in headings and inline sentences. USPTO and DoW configure no third tier (no `UnitOption.offices`), so their `subUnit`/`subUnitPlural` are generic fallbacks that never render today.

Components read the words from `getTenant().tierLabels` and lowercase inline where the sentence needs it (`Every ${tiers.unit.toLowerCase()}'s sign-off progress`), rather than pluralizing by appending `"s"` — that ad-hoc plural is what `unitPlural` replaces. Call sites: `app/admin/page.tsx`, `components/admin/approval-transparency.tsx`, `bureau-rollup.tsx`, `form-config-panel.tsx`, `office-rollup.tsx`, `user-management.tsx`, `components/dashboard/bureau-dashboard.tsx`, `department-dashboard.tsx`, `orientation-banner.tsx`, `components/landing/cross-program-impact.tsx`, `public-landing.tsx`, `components/steps/step-1-submitter-info.tsx`, and `components/submissions/submission-detail.tsx`.

**The view-model layer resolves tier vocabulary too, and `tenantHasBureauTier()` is not a substitute for doing so.** The dashboard builders were initially left alone on the reasoning that their org-tier strings sit behind that gate and so can't leak to USPTO or DoW. The reasoning is sound and the conclusion is wrong: the gate tests whether any `unit.options` entry declares `focusAreas`, which every bureau-tier tenant satisfies — Commerce today, ES2 next. It decides *whether* a bureau-tier card, action, or drill-down renders; it says nothing about *what words* it uses. #### OMB federal AI use case inventory: fields, export, and reportability

OMB M-25-21 companion-guidance fields — `stageOfDevelopment`, `highImpact` (three-way: high-impact / presumed-but-not / not high-impact), `highImpactJustification`, `topicArea`, `aiClassification`, `highImpactFactors`, `hasATO`, `systemSource`, `hasPii`, `demographicFeatures`, `nationalSecuritySystem`, `researchOnly`, and the 9 high-impact-only risk-management fields (`lib/steps.ts`) — are each registered in `lib/fieldRegistry.ts` with `omb: true`. As of issue #162, none of these render in the *submitter* wizard at all (that whole block used to be Step 7, Feasibility & Security — removed from idea intake entirely, not just gated). A reviewer fills them in during vetting via `components/submissions/governance-capture-panel.tsx` (see "Vetting-side governance capture" below); the `FieldRequirementBadge` (`components/launchpad/field-requirement-badge.tsx`, issue #60) that used to annotate them in the wizard now only appears in the admin Form Configuration panel (`components/admin/form-config-panel.tsx`) and the governance capture panel. All are optional at the field-registry level, so USPTO/DoW tenants that don't fill them in are unaffected.

Four pieces of pure, unit-tested logic build on those fields:

- **Export** — `lib/ombExport.ts`'s `OMB_COLUMNS` is the full public-inventory schema: 33 of OMB's 34 data-dictionary columns (`docs/omb-2025-inventory-fields.md`, exact OMB column names/allowed values; `id` is dropped — see redaction below) plus three LaunchPad-added columns that predate this schema ("Agency", never a form field — read from the tenant at export time; "Reporting Mode"/"Consolidated Category", sourced from `determineConsolidation()`, see below). All 9 `hi_*` high-impact risk-management columns (#26-34) are populated only when a row is both `highImpact: "high_impact"` and `stageOfDevelopment: "deployed"` — blank for every other row, mirroring the wizard's own `showWhen` gate for that field group. `mapSubmissionToOmbRow(submission, agency)` takes an `{ shortName, publicInquiryEmail }` context rather than a bare tenant name, since both feed the export (`app/api/export/omb/route.ts` builds it from `getTenant()`). `buildOmbCsv()` emits one row per **individually**-reported submission (every high-impact use case is always in this group), then — instead of one row per bureau — a single department-level row per **consolidated** category (e.g. `"Email prioritization & categorization (consolidated)"`), listing which bureaus and how many submissions it stands in for. Rows are ordered by `CONSOLIDATION_CATEGORIES` (not submission order), so the export is deterministic regardless of input sort order. The four DoC/EO risk-management questions (`involvesSensitiveData`, `aiDecisionalImpact`, `aiModelSourcing`, `aiHumanReview`) are intentionally absent — they're a distinct Commerce mandate, not part of OMB's 34-field schema (see the field-cascade section below).
- **Public-inventory redaction** (issue #117) — this is the *public* OMB inventory export, so `docs/omb-2025-inventory-fields.md`'s public-reporting rules apply unconditionally, not just to withheld rows: the internal use-case id (#1) is never a column at all (OMB permits omitting it from the public inventory); `contact_email` (#4) is always `TenantConfig.publicInquiryEmail` — a monitored public-inquiry inbox, never a real submitter's address; and any submission whose `isWithheld` (#5) answer isn't `"no"` is excluded from the CSV entirely by `isPubliclyReportable()`, applied before consolidation grouping so a withheld use case can't leak even indirectly (e.g. inflating a consolidated row's bureau count). `app/api/export/omb/route.ts` also runs `migrateFormData()` on each row before export — the export route reads Supabase directly rather than through `lib/adapters/default/supabaseStore.ts`'s `getSubmissions()`, so without this it would skip the legacy `publicIndicator` → `isWithheld` migration (`lib/formDataMigrations.ts`) that `is_withheld` redaction depends on.
- **Consolidated vs. individually-reported classification** — `lib/ombConsolidation.ts` (`determineConsolidation`) is the cross-bureau rationalization piece: it classifies a use case as **Consolidated** (matches one of OMB's ~19 "widely used commercial AI" categories from the 2025 reporting guidance/cheat sheet — e.g. email triage, meeting transcription, code generation, enterprise search — which a department reports **once** across every bureau) or **Individual**. Matching is deterministic regex over the submission's free text (`useCaseTitle`, `useCaseDescription`, `coreProblem`, `problemDefinition`, `proposedSolution`, `solutionSummary`, `businessValue`) against `CONSOLIDATION_CATEGORIES`, so a match is always explainable by the pattern that fired — no ML. This is category matching, a different question from `lib/similarity.ts`'s text-overlap dedup (which flags two submissions that look like the *same idea*, regardless of category). **High-impact use cases are always `Individual`, never `Consolidated`** (coordinates with the high-impact determination below); the category match is still surfaced in that case (`category`/`categoryLabel`) so a reviewer can see *why* an otherwise-consolidatable use case is being reported on its own. The result is shown on the submission detail view (an "OMB reporting mode" card next to "OMB reportability") and as a "Consolidated (OMB)" count column plus a department-wide "consolidates to M OMB reportable entries" summary in the bureau roll-up (`components/admin/bureau-rollup.tsx`). The DoC seed (below) includes a cross-bureau consolidated trio so this summary line visibly collapses (12 use cases → 10 OMB reportable entries) instead of reading 1:1 with the submission count — see [issue #33](https://github.com/mattshanklePA/launchpad-v0/issues/33).
- **Reportability determination** — `lib/ombReportability.ts` (`determineReportability`) decides *whether* a use case must be reported at all, per the OMB "Guidance on 2025 Agency AI Reporting" (June 27, 2025) and the OMB AI Inventory Reporting Cheat Sheet: include at any stage of development if it supports mission/service delivery, enhances internal decisions, or benefits the public; exclude National Security System/Intelligence Community use or research-only use; a research-only use that controls or significantly influences a decision about individuals is reportable despite being research. When a required input (stage, NSS, or research-only) hasn't been answered yet, the result is `"review"`, erring on the side of inclusion. The result (`status` + one-line `reason`) is surfaced on the submission detail view (`components/submissions/submission-detail.tsx`) and as an "OMB review needed" count column in the bureau roll-up (`components/admin/bureau-rollup.tsx`).
- **High-impact determination** — `lib/highImpactDetermination.ts` (`determineHighImpact`) *recommends* whether a use case meets OMB's high-impact AI definition (M-25-21 Section 5) instead of trusting a bare self-reported flag. Two layers feed the recommendation: (1) the manual path — the submitter marks which of the five Section 5 categories the AI output could meaningfully affect — rights, safety, access to benefits, resource allocation, or enforcement actions (`highImpactFactors`); (2) an inference layer on top, added for [issue #27](https://github.com/mattshanklePA/launchpad-v0/issues/27) so the recommendation isn't blind to risk signals LaunchPad already captures elsewhere — decisional AI (`aiDecisionalImpact === "yes"`, the same field `lib/riskProfile.ts` reads) infers **rights**; a high-`severity` problem whose problem/solution text names a life-safety scenario infers **safety**; decisional AI whose problem/solution text names benefits/eligibility, resource-allocation, or enforcement/adjudication language infers **access to benefits**, **resource allocation**, or **enforcement actions** respectively. Free text is always a secondary signal that narrows or corroborates a structured field (`aiDecisionalImpact`/`severity`) — it never triggers a category by itself. The function recommends `"yes"` (with one reason per flagged-or-inferred factor) if any category applies from either layer, else `"no"`. The submission detail view shows this recommendation alongside the reasons and lets the reviewer set the final `highImpact` call (`patchSubmissionFormData`) — advisory, the same pattern as Scout's read on a submission; the rule-based check, not Scout, is the source of truth.

  `highImpact` is OMB's exact three-way field (`"high_impact"` / `"presumed_not_high_impact"` / `"not_high_impact"`, docs/omb-2025-inventory-fields.md field #7) — not a Yes/No. Selecting `"presumed_not_high_impact"` reveals `highImpactJustification` (field #8), a required free-text explanation. Setting `highImpact` to `"high_impact"` **and** `stageOfDevelopment` to `"deployed"` reveals all 9 M-25-21 minimum-practice risk-management fields (#26-34) in the wizard: `preDeploymentTesting`, `aiImpactAssessmentCompleted`, `aiImpactAssessment`, `independentReviewConducted`, `ongoingMonitoringPlan`, `operatorTrainingEstablished`, `failSafeMechanism`, `humanOversightAppeal`, and `publicConsultationSteps` (select-multiple) — a pre-deployment or pilot high-impact idea has nothing to assess/monitor/appeal yet, so the group stays hidden until fully deployed (issue #60's `showWhen` conditional-disclosure predicate, see below). Every multiple-choice field in this group permits an "In-progress" and a CAIO-waiver answer, not just Yes/No — reconciled exactly against the doc's data dictionary (issue #65).

**Conditional disclosure (`showWhen`, issue #60)** — on top of the cascade (`fieldsForBureau`) and the admin on/off toggle (`isFieldEnabled`), a `FieldDefinition` can carry `showWhen?: (formData: FormData) => boolean`: a field renders only once its prerequisite is met, so a pre-deployment, non-high-impact submission isn't asked all ~34 OMB questions up front. Wired onto every conditional field in the registry: the 9 M-25-21 high-impact risk fields (`highImpact === "high_impact" && stageOfDevelopment === "deployed"`); `highImpactJustification` (`highImpact === "presumed_not_high_impact"`); `topicArea`/`aiClassification` (any non-empty, non-`"retired"` `stageOfDevelopment`); `hasATO`, `systemSource`, `operationalDate`, `trainingDataDescription`, `hasPii`, `demographicFeatures`, and `customCode` (`stageOfDevelopment` is `"pilot"` or `"deployed"`); `atoSystemName` (`hasATO === "yes"` **and** pilot/deployed) and `systemSourceVendorName` (`systemSource` is `"contract"`/`"vendor"` **and** pilot/deployed) — both doc-required sub-fields compound their parent-answer gate with the stage gate, not just the parent answer; `openSourceCodeLink` (`customCode === "yes"`); and `accessControlRequirements` (`involvesSensitiveData === "yes"`). The three optional-and-never-required fields (`link_to_data`/`federalDataCatalogLink`, `pia_url`/`piaLink`, `code_url`/`openSourceCodeLink`) are never in `lib/submissionReadiness.ts`'s required-field list, so they can't block submit even though `openSourceCodeLink` still uses `showWhen` for its own conditional visibility. `isFieldVisible(fieldKey, formData)` (`lib/formConfig.ts`) is the single resolver combining all three checks (cascade + enabled + `showWhen`); the wizard's `useFieldVisibility(formData)` hook and `lib/submissionReadiness.ts`'s required-at-submit check both call through it, so "still needed to submit" can never demand a field the submitter can't currently see.

#### Cutting OMB intake burden: auto-fill and AI-propose (issue #61)

Most of the 34-field OMB set doesn't need a submitter to author it from scratch — it's already known from their profile, from the wizard they fill anyway, or is a judgment call the app can propose and let them confirm. Two mechanisms, additive on top of the field-config cascade above:

- **Profile and wizard-answer reuse (zero new code)** — Agency/Bureau/Component/Email are never re-asked: `profileFromSession()` (`context/form-context.tsx`) pre-fills `submitterOffice`/`submitterSubOffice`/`submitterEmail` from the logged-in user's session on first load, and "Agency" itself is never a form field at all — it's read from `getTenant().shortName` at export time (`lib/ombExport.ts`). The free-text OMB columns "What problem is the AI intended to solve?", "Expected benefits and positive outcomes", and "Describe the AI system's outputs" are likewise never double-entered — `lib/ombExport.ts` maps `coreProblem`/`businessValue`/`solutionSummary` directly to those columns, so the wizard fields themselves *are* the OMB answers, not a second copy to keep in sync. `systemSource` (built in-house/under contract/purchased) and `customCode` are native OMB-registry fields with no earlier duplicate to reuse from either.
- **AI-proposed, submitter-confirmed fields** — `lib/ombAutofill.ts` is the central engine for the fields that genuinely need a judgment call, not just a lookup: `proposeHighImpact` (wraps `determineHighImpact`, mapping its binary yes/no onto OMB's three-way `highImpact`), `proposeTopicArea` and `proposeAiClassification` (new deterministic-regex modules, `lib/useCaseTopicArea.ts` and `lib/aiClassificationDetermination.ts`, built in the exact style of `lib/ombConsolidation.ts`'s category matching — first keyword match over the problem/solution text wins, so a proposal is always explainable by the pattern that fired, no ML), and `proposeIsWithheld` (OMB's four-way "should this be withheld?" field #5 — defaults to "No" unless `nationalSecuritySystem`/`securityClassification` already flags a specific withholding reason). A fifth function, `proposeHasPii`, isn't a judgment call at all — it reuses the Department's `involvesSensitiveData` answer (a separate mandate from OMB's `hasPii`, per the field doc, but the same underlying fact) instead of asking the near-duplicate PII question again. Every proposal function returns `{ value, rationale } | null` — `null` (never a guessed value) when the engine can't confidently derive anything, e.g. `topicArea`/`aiClassification` with no keyword match in the free text.
- **Wiring** — `hooks/use-ai-propose.ts`'s `useAiPropose()` pre-fills a field from its proposal the first time it's empty, guarded by a ref so it never fires twice and never clobbers a submitter's own answer or a later override back to blank. `components/launchpad/ai-proposed-hint.tsx` renders the one-line rationale under the field (or, when the proposal is `null`, an amber "couldn't confidently propose a value — please select one" flag) so the viewer always sees *why* before confirming or overriding. `isWithheld` is still wired into the wizard's Idea Overview step (`step-2-use-case-overview.tsx`, Step 5 of idea intake); `highImpact`/`topicArea`/`aiClassification`/`hasPii` moved out of the wizard with the rest of the Feasibility & Security block (issue #162) and are now wired into `components/submissions/governance-capture-panel.tsx` instead — everywhere else, the field is either profile/wizard-derived (no proposal needed) or a plain judgment call with no reliable heuristic (`systemSource`, `customCode` — proposing from `aiModelSourcing`, a geography-of-build question, would be a fabricated inference, not a derivation, so neither is auto-proposed).
- **"Still needed to submit" reuses `isFieldVisible`, not a second resolver** — every OMB/M-25-21 field check in `lib/submissionReadiness.ts` is a `needInto(target, fieldKey, ..., test)` call, and `needInto()` already gates on `isFieldVisible(fieldKey, formData)` before running `test()`. So extending coverage to, say, the 9 M-25-21 minimum-practice fields required *only* adding the `omb()` calls — the `highImpact === "high_impact" && stageOfDevelopment === "deployed"` gate already lives in `lib/fieldRegistry.ts`'s `showWhen` and is applied automatically; nothing in `submissionReadiness.ts` re-implements it. As of issue #160 (below), these checks land in `governanceMissing` rather than `missing`, so "still needed" is scoped both to what the submitter can currently see *and* to what's actually required at the idea stage.

#### Two-stage lifecycle: idea vs. use case, governance fields gated to vetting (issue #160)

Feedback from the USPTO LaunchPad instance: intake mixed raw *ideas* with vetted *use cases*, and forced OMB/feasibility/RMF governance work at submission time even though a fresh idea has no ATO, no deployment stage, and nothing to monitor yet. LaunchPad now treats these as two explicit stages of the same submission record — no new field or migration, since the review workflow already carries everything needed to derive it:

- **Lifecycle stage is derived, not stored** — `lib/reviewWorkflow.ts`'s `getLifecycleStage(submission)` returns `"idea"` for every pre-approval `SubmissionStatus` (`draft`/`submitted`/`in_review`/`needs_info`/`rejected`) and `"use_case"` only once a reviewer sets `status: "approved"`. `LIFECYCLE_STAGE_LABEL` and `lifecycleStageBadgeClasses` (routed through the shared `STATUS_BADGE_CLASS` vocabulary — `healthy` for a vetted use case, `neutral` for a still-raw idea, since being an idea isn't itself a problem) back the single UI primitive, `components/ui/lifecycle-badge.tsx`'s `LifecycleBadge`, so every surface renders the same label/color instead of independently reinventing "Idea"/"Use Case" copy. Wired into the submitter's "My ideas" list (`components/dashboard/personal-dashboard.tsx`), the reviewer queue board (`components/dashboard/queue-board.tsx`), Decision Center (`components/admin/decision-center.tsx`), and the submission detail header (`components/submissions/submission-detail.tsx`).
- **The idea intake gate no longer requires governance fields** — `lib/submissionReadiness.ts`'s `getSubmissionReadiness()` is the *idea* gate: the OMB 34-field inventory, the M-25-21 minimum-practice block (fields #26-34), and the two NIST AI RMF gap fields (`disseminatesToPublic`/`scalable`) are no longer part of `missing`/`canSubmit`/`completenessPercent` — a submitter can submit an idea with all of them blank. Those checks still run with the exact same `showWhen`-aware gating (via a shared `needInto(target, ...)` helper that the ordinary idea-required `need()` and the governance-only `omb()` both call), but land in a new `governanceMissing: MissingItem[]` array on the returned `SubmissionReadiness` — tracked for the vetting stage, informational only, never blocking. The four DoC/EO AI-risk-mandate questions (`involvesSensitiveData`, `aiDecisionalImpact`, `aiModelSourcing`, `aiHumanReview` — a distinct Commerce mandate, not part of OMB's 34-field schema or M-25-21/RMF) are unaffected and stay required at idea intake, same as before.
- **Non-breaking** — no field was removed from `FormData`, `lib/fieldRegistry.ts`, or the wizard steps; `lib/ombExport.ts`'s public inventory export and every reviewer surface (bureau roll-up, Decision Center, submission detail, RMF profile) read the same fields exactly as before regardless of whether they were "required" to submit. Only `lib/submissionReadiness.ts`'s idea-gate classification changed. Slimming the intake wizard itself (deferred here) is done by issue #162 (below); a dedicated vetting-stage readiness gate on top of `governanceMissing` remains tracked as follow-on work.

#### Vetting-side governance capture: reviewers complete what issue #160 gated out of intake (issue #161)

Issue #160 (above) stopped requiring the OMB inventory / M-25-21 / RMF-input fields at idea submission, but left no reviewer-facing place to actually fill them in — `governanceMissing` was informational only. This issue gives reviewers that surface, reusing the propose-then-confirm pattern `lib/rmfProfileReview.ts` already established for the RMF profile.

- **`lib/governanceCapture.ts`** is the propose-then-confirm record for governance fields, mirroring `rmfProfileReview.ts`'s shape but flattened for ~25 independent fields instead of one computed value: `GOVERNANCE_FIELD_KEYS` (re-exported from `lib/submissionReadiness.ts`, so the readiness gate's `governanceMissing` list and the capture panel's field list can never drift apart), `applicableGovernanceFields(fd)` (the same `isFieldVisible` gate the wizard and the readiness check use, so a field hidden by `showWhen` is never demanded here either), and `buildGovernanceCapturePatch(draft, finalValues, opts)` — builds one `form_data` patch containing both the final field values themselves (under their normal `FormData` keys, e.g. `stageOfDevelopment`, `topicArea` — never a shadow copy) and a `governanceCaptureReview` audit record (`{ entries: [{ field, decision: "confirmed" | "overridden", proposedValue, finalValue }], byName, byEmail, at }`) noting per field whether the reviewer kept Scout's draft or changed it. `getGovernanceCaptureReview(submission)` reads it back, same cast-from-`form_data` pattern as `getRmfProfileSnapshot`/`getRmfProfileReview`.
- **Scout's draft (`app/actions.ts`'s `draftGovernanceFields`)** never invents a second rubric: fields with an existing deterministic determination (`highImpact`/`topicArea`/`aiClassification`/`hasPii`) reuse `lib/ombAutofill.ts`'s proposers directly. Facts an LLM can't know from idea text (`hasATO`, `stageOfDevelopment`) and the M-25-21 minimum-practice status fields get a conservative, non-LLM default instead of a model call — a use case still in vetting hasn't gotten an ATO, done pre-deployment testing, or moved past pre-deployment, so "not yet" is the honest default, not a guess. Only the fields that are a genuine judgment call on free text (`disseminatesToPublic`, `scalable`, `customCode`, `trainingDataDescription`, `aiImpactAssessment`, `demographicFeatures`) go to `generateObject`/`getModel()`, drafted from the idea's problem, solution, expected benefits, and constraints — with a deterministic fallback (conservative low-risk defaults, `aiImpactAssessment` assembled directly from the problem/solution/business-value text) if the model call throws, same guardrail every other Scout action in `app/actions.ts` follows.
- **`components/submissions/governance-capture-panel.tsx`**, wired into the reviewer decision checklist in `components/submissions/submission-detail.tsx` as a new "Complete the use case" item (between High-impact determination and NIST AI RMF, since RMF's Map/Measure/Manage functions read many of the same fields). Drafts on open, seeds each applicable field from the submission's existing value if already answered or Scout's proposal otherwise (mirroring `lib/ombAutofill.ts`'s "pre-fill only while empty" rule), and recomputes which fields are currently applicable against the reviewer's in-progress edits (not just the saved submission) so, e.g., setting Stage of Development to "Deployed" immediately reveals the ATO/vendor/training-data fields without a save round-trip. A single Save records confirm/override per field automatically — no separate confirm/override button pair per field — based on whether the reviewer's final value differs from Scout's proposal. Field option lists (`lib/governanceFieldOptions.ts`) are this panel's own source of truth for these labels — as of issue #162 the submitter wizard no longer renders this block at all (the old `step-8-feasibility-security.tsx` was deleted), so this panel is the only surface that needs them.
- **No changes needed to the compute layer** — `lib/ombReportability.ts`, `lib/ombConsolidation.ts`, `lib/highImpactDetermination.ts`, `lib/nistRmf.ts`, and `lib/ombExport.ts` already read governance fields straight off `FormData`/`Submission`, not off a separate reviewer-only store, so completing them here is immediately visible to reportability, consolidation, high-impact, RMF, and the OMB export with zero code changes to those modules — only `governanceCaptureReview` is new, as a pure audit trail on top.

#### Slimming intake to a 5-step idea flow (issue #162)

Issue #160 stopped *requiring* the OMB/M-25-21/RMF governance block at idea intake; issue #161 gave reviewers a place to fill it in during vetting. That left the submitter wizard itself unchanged — still 10 steps, still rendering the full Feasibility & Security block (just no longer blocking submit on it) plus a submitter self-rated `severity` field, which is what was actually driving submitters to abandon the form mid-way. Issue #162 finishes the job by cutting the wizard down to a fast, 5-step idea flow:

- **New step map** — `lib/steps.ts`'s `getFormSteps()` now returns 7 steps total: 1 Submitter Info, 2 Business Problem & Opportunity, 3 Proposed Solution & Expected Benefits, 4 Technical Constraints, 5 Idea Overview, 6 Review & Submit, 7 Submission Complete. Steps 2-6 are the "5-step idea flow" the issue names; Submitter Info and the confirmation page bookend it, same shape as before.
- **What got cut, and where it went** — Strategic Alignment (`usptoFocusArea`/`relevantOkrs`/`alignmentSummary`) and Success Metrics (`successMetrics`/`keyMetrics`/`timelineForResults`/`metricsSummary`) are no longer collected at intake at all — no wizard step renders them anymore, joining the OMB/M-25-21 block issues #160/#161 already moved to vetting-only. The submitter *self-rating* fields — `severity` (problem step), `implementationComplexity`/`userTimeSavings`/`costSavings` (solution/value step) — are also dropped from intake: value and impact are a Scout/reviewer determination, not something a submitter grades on their own idea. Step 4 (Technical Constraints) replaces the old Feasibility & Security step (`Step8FeasibilitySecurity`, deleted) with a single free-text field reusing the existing `dependencies` FormData key — light notes only, no self-graded feasibility, no OMB/M-25-21 fields. Every removed field stays in `FormData`/`lib/fieldRegistry.ts` unchanged — nothing here is a data-model or OMB-export change, only a wizard-UI and readiness-gate change. `lib/fieldRegistry.ts` moves the now-intake-absent fields' `step` numbers to sentinels (15/16/17, documented inline) so they don't collide with the new step numbers `isStepEnabled`/`findNextEnabledStep` use for real wizard navigation.
- **Merged steps** — `components/steps/step-3-solution-benefits.tsx` (new) combines the old separate Proposed Solution and Value steps into one screen: the submitter describes the solution and what they *expect* it to deliver, explicitly framed as an expectation for a reviewer to confirm, not a determination. `components/steps/step-3-problem-and-users.tsx` (kept, `severity` removed) still leads with the problem, then who's affected.
- **Two field-grouping models, decoupled** — `lib/steps.ts`'s `formPhases` (3 entries: Setup / Your Idea / Summary & Submit) now describes only the wizard's own phase-grouped progress bar and left nav (`wizard-nav.tsx`, `progress-bar.tsx`), spanning just steps 1-6. A separate `adminFieldGroups` (5 entries, the old `formPhases` content unchanged) is what `components/admin/form-config-panel.tsx` groups by — it still needs a home for every `FIELD_REGISTRY` field, including the vetting-only ones, and reusing the wizard's slimmed `formPhases` for that would either drop those fields from the admin panel entirely or add always-empty phantom segments to the wizard's own progress bar.
- **Readiness gate follows the wizard** — `lib/submissionReadiness.ts`'s `REQUIRED_FIELD_KEYS`/`need()` calls only cover the fields the 5-step flow actually collects; `severity`/`implementationComplexity`/`userTimeSavings`/`costSavings`/Strategic Alignment/Success Metrics are simply never checked (not even in `governanceMissing` — that bucket stays scoped to the OMB/M-25-21 fields issues #160/#161 already covered). `assessReadiness` (`app/actions.ts`) — the AI readiness check on the Review & Submit step — was re-scoped the same way, so it never grades an idea down for a dimension the wizard no longer asks about.
- **Scout coaching kept, re-pointed** — `components/launchpad/chat-panel.tsx` and `app/actions.ts`'s `validateAndRefineInput` still coach one question at a time on each remaining step (2, 3, 4); the per-step rubrics/formatting guidance were rewritten for the merged/slimmed steps rather than removed.
- **Deferred** — `suggestStrategicAlignment` (`app/actions.ts`) and `lib/strategicFocusAreas.ts` are unused by the wizard now but left in place, unremoved, as a starting point if a future issue adds vetting-side alignment capture (the same propose-then-confirm shape issue #161 used for OMB/M-25-21).

#### Multi-field assistant drafts: `{ fieldKey: { value, rationale } }` (issue #168)

Before this issue, every coaching step (`app/actions.ts`'s `validateAndRefineInput`) ended its Q&A with a single `scaffoldText` string, and `AIdChatPanel` wired that string to exactly one FormData field via `onApplySuggestion`. That undersold the merged Propose-a-Solution step (issue #162, above): its Q&A already gathers the user- and business-benefit specifics, but the old shape could only land the draft in `solutionSummary` — `userValue`/`businessValue` stayed blank even though the assistant had everything it needed to draft them too.

- **`ScoutResponse`'s scaffold variant is now `{ mode: "scaffold", summary, fields: Record<string, ScoutFieldDraft> }`** (`app/actions.ts`) — `ScoutFieldDraft` is `{ value, rationale }`, the same propose-then-confirm shape `lib/governanceCapture.ts`'s `GovernanceFieldProposal` already established for the vetting-side draft engine. `scaffoldText` is gone; every step drafts a keyed bundle of its own output fields instead of one field regardless of how many the step actually collects.
- **`lib/scoutFieldPlan.ts`** is the new single source of truth for which FormData fields a step drafts: `SCOUT_STEP_FIELD_PLAN` maps step number → `{ key, label }[]` (step 3, Propose-a-Solution, plans all three: `solutionSummary`, `userValue`, `businessValue` — reusing the existing `lib/steps.ts` keys named in the issue, not a parallel field set). `scoutFieldsForStep(step, enabledFields)` filters that plan against the admin form config's `enabled` map (the same shape `buildStepInputs`/`isFieldVisible` already read) so the assistant never drafts a field an admin turned off. `draftFieldFallback(label, seedText)` is the deterministic, no-AI fallback per field — reuses the submitter's own seed text verbatim and appends `[BRACKETED PLACEHOLDERS]` for what's missing, same anti-fabrication guardrail the AI path follows, used both by `getMockResponse` (API unavailable) and per-field when the model's response for that field comes back empty. Pulled into its own module (rather than staying inline in `app/actions.ts`) so the plan and the fallback's placeholder behavior are unit-tested (`lib/scoutFieldPlan.test.ts`) without mocking the AI SDK.
- **`validateAndRefineInput`** builds its `generateObject` schema's `fields` sub-object dynamically from `scoutFieldsForStep(step, enabledFields)`, so the model is constrained to draft exactly the named fields for that step — never a field the step doesn't render or the admin disabled. The system prompt's SCAFFOLD MODE instructions were generalized from "produce the scaffoldText template" to "draft every named field," with per-field formatting hints (`fieldFormattingHints`) carried in each field's own schema `.describe()` rather than one step-wide formatting block. The one-question-at-a-time Q&A loop, the suggested-answer chips, and the anti-fabrication rules (`[BRACKETED PLACEHOLDERS]`, never invent numbers/units/programs) are unchanged — only the final answer's shape changed from one string to one draft per field.
- **`AIdChatPanel`'s `onApplySuggestion` is now `(fields: Partial<FormData>) => void`** (`components/launchpad/chat-panel.tsx`) instead of `(suggestion: string) => void`. A scaffold message renders one card per drafted field (label from `lib/fieldRegistry.ts`'s `FIELD_REGISTRY_BY_KEY`, falling back to a Title-Cased field key for anything unregistered) with its own "Apply {field}" button calling `onApplySuggestion({ [key]: value })`, plus an "Apply All" button (shown only when a step drafts more than one field) calling `onApplySuggestion(allFields)`. Every step's `handleSuggestion` collapsed to the same one-liner — `(fields) => setFormData((prev) => ({ ...prev, ...fields }))` — since applying one field or all of them is just a partial-FormData merge either way; no step needs its own per-field switch statement.
- **Steps 2 and 4 keep a single-field plan** (`problemDefinition`, `dependencies` respectively) — the multi-field capability is additive per step, not a forced minimum; a step with one output field just renders one card and no "Apply All" button. Only step 3 (Propose-a-Solution) currently plans more than one field, matching this issue's acceptance criteria.

#### Conversational-first idea intake (issue #169)

The 5-step wizard (issue #162, above) is still a *form* the submitter drives, with Scout as a per-step helper panel (`AIdChatPanel`, gated on a pre-typed seed field). Issue #169 adds a second, conversational-first way to complete the same bare-minimum idea fields: one continuous assistant thread that leads the whole flow, with a live "your idea so far" record next to it that fills in as the thread progresses and stays editable throughout. Optimized for an occasional submitter — tap-first, not type-first — and deliberately asks for less than the wizard's full gate: only business problem/opportunity, proposed solution, expected benefits (user + business), affected business unit, and internal/external. Reviewers request anything more via the existing `needs_info` flow, same as any other gap found during vetting; the OMB/feasibility/RMF fields are vetting-side (issue #161) regardless of which intake path was used.

- **`lib/intakeFlow.ts`** is the pure, unit-tested (`lib/intakeFlow.test.ts`) sequencing logic: `INTAKE_TOPICS` is an ordered list of the light fields (problem → affected business unit(s) → internal/external → solution & expected benefits), each tagged `kind: "draft"` (AI-drafted, reusing an existing `SCOUT_STEP_FIELD_PLAN` step) or `kind: "choice"` (a short closed pick, asked locally with no model call). `isTopicCaptured`/`nextIntakeTopic`/`intakeMinimumMet` are pure functions of `FormData` — there is no separate step pointer or conversation-position state to keep in sync. `activeIntakeTopics` filters through `isFieldEnabled` so an admin-disabled or bureau-out-of-scope field's topic is skipped, same posture as `scoutFieldsForStep`.
- **`components/launchpad/conversational-intake.tsx`** is the orchestrator, mounted at `/submit/conversational` (nested under `app/submit`'s existing `RequireAuth` + `FormProvider` + `DashboardShell` layout, so it shares the exact same `FormData`/draft persistence as the step wizard — an idea started in one can be finished in the other). A `useEffect` recomputes `nextIntakeTopic(formData)` on every `FormData` change and starts that topic's opening turn exactly once (tracked in a ref, not React state, so it never re-fires for a topic already asked or already captured). "draft" topics call the same `validateAndRefineInput` server action `AIdChatPanel` uses (step 2's `problemDefinition` plan, step 3's `solutionSummary`/`userValue`/`businessValue` plan) with an empty conversation history and no pre-typed seed — the model's own turn-count heuristic still opens with a clarifying question, so no separate "type a draft first" box is needed; a scaffold reply is applied to `FormData` immediately (no manual "Apply" step) since the record panel *is* the apply surface. "choice" topics (affected business unit(s), internal/external) render suggested-answer chips sourced directly from the tenant's `affectedSystems` list or a fixed two-option enum, with no AI call — multi-select needs an explicit "Continue" chip, single-select commits on tap.
- **Reuse, not a fork, of the existing engine** — `ScoutResponse`, `validateAndRefineInput`, and `SCOUT_STEP_FIELD_PLAN` (issue #168, above) are used as-is; `fieldLabel` (the `FIELD_REGISTRY_BY_KEY`-backed label lookup) is now exported from `chat-panel.tsx` so both panels name the same `FormData` keys identically. `AIdChatPanel` itself isn't reused verbatim — it's scoped to one wizard step with one field plan and a pre-typed-seed gate, none of which fits "one thread across several fields, chip-first, no seed box" — but its Q&A/chip visual language and the underlying engine are the same.
- **`components/launchpad/intake-record-panel.tsx`** is the live, always-visible "your idea so far" record: one section per `INTAKE_TOPICS` entry, each showing its captured value(s) with an inline "Edit" control (a textarea for drafted text, the same tenant-driven toggle-chip multi-select the wizard's own problem step uses for affected business units, `OptionRadioGroup` for internal/external). Saving an edit calls back into the orchestrator's `onFieldChange`, which merges the patch into `FormData` and appends a short acknowledgment into the thread — since sequencing is driven purely by `FormData` content, a field filled in here (even one the assistant hasn't asked about yet) is simply already "captured" the next time `nextIntakeTopic` looks, so the assistant never re-asks it. The panel's footer doubles as the review-and-submit step: once `intakeMinimumMet(formData)` is true it shows a "Submit for Vetting" button (best-effort `assessReadiness` call, then `saveSubmission`, then a redirect to the new submission's detail page) instead of the wizard's `SubmissionGate`/`getSubmissionReadiness`, which gates on a larger field set (target audience, idea title/description, AI quality score) this flow deliberately doesn't collect.
- **Accessibility** — the message list is `role="log" aria-live="polite"` so new assistant turns are announced without stealing focus; every chip is a real `<button>` (native keyboard support), multi-select chip groups use `role="group"`/`aria-pressed`, single-select groups use `role="radiogroup"`/`role="radio"`, matching the pattern `components/launchpad/option-radio-group.tsx` already established elsewhere in the wizard.
- **Deferred (now resolved by issue #170 below)** — the toggle to switch between the conversational thread and the step-by-step wizard for the *same* in-progress draft, called out above as a follow-up, is issue #170's "Guided/Form mode toggle."

#### Guided/Form mode toggle (issue #170)

Issue #169 (above) shipped Guided and Form as two independently-reachable routes with no way to move between them once you'd picked one. This issue adds the toggle it deferred, so a submitter can compare both live on the same in-progress idea instead of committing to one up front.

- **One shared surface, not a route swap** — `components/launchpad/intake-mode-surface.tsx`'s `IntakeModeSurface` renders the `IntakeModeToggle` plus whichever of `ConversationalIntake`/`FormContainer` is active, and both `app/submit/page.tsx` and `app/submit/conversational/page.tsx` now render it (instead of rendering their respective component directly). Because both routes already sit under the same `app/submit/layout.tsx` `FormProvider`, and switching mode here is a plain React state change (which child is mounted) rather than a navigation, no `FormData` is ever read from or written to twice, and nothing entered so far can be lost switching either direction — this is the same guarantee issue #169 already established for the two routes, just exercised without a page transition in between.
- **`hooks/use-intake-mode-preference.ts`** — `useIntakeModePreference()` holds the current mode plus a `setMode` that persists it to `localStorage`, namespaced per signed-in user via the existing `lib/draftStorage.ts` `scopedDraftKey` helper (`aid-intake-mode:<userId>`) — the same per-user scoping the wizard draft itself uses, and for the same reason (one shared browser, multiple accounts, no cross-account leakage). SSR-safe: renders `"guided"` until mounted, then syncs from storage — a submitter with no stored choice yet (a brand-new account, or a browser that's never visited `/submit`) simply stays on that default, satisfying "new submitters default to Guided" with no separate first-run flag to maintain.
- **The toggle** — `components/launchpad/intake-mode-toggle.tsx`'s `IntakeModeToggle` is a single `components/ui/switch.tsx` `Switch` (Radix, so Space/Enter/click all work and it's tab-reachable with no extra wiring — 508) labeled `Guided`/`Form` on either side inside a `role="group" aria-label="Intake mode"` wrapper, with an `aria-label` on the switch itself describing the current and target mode. Deliberately tenant-neutral copy (`Guided`/`Form`, not a tenant's assistant name) so it reads identically on every deployment.
- **`/submit/conversational` still means Guided** — `IntakeModeSurface` takes an optional `forcedInitialMode`; the conversational route passes `"guided"` so the dashboard's "Talk to `<assistant>`" link keeps its existing meaning regardless of whatever mode the submitter last toggled to, while also updating their remembered preference. `/submit` passes nothing, so it always reflects the submitter's own remembered choice (defaulting to Guided, as above).
- **Lightweight instrumentation** — `FormData.intakeMode` (`lib/steps.ts`, optional, absent on drafts and on submissions saved before this field existed) is stamped `"guided"` or `"form"` at the moment of submit — `conversational-intake.tsx`'s `handleSubmit` and `step-10-review-submit.tsx`'s `handleSubmitForVetting` — and flows into `form_data` through the existing `saveSubmission` path with no schema migration (it's a JSON column). This doesn't build a full funnel (no separate "mode selected" event, so a true drop-off *rate* per mode isn't computable yet), but it's enough to compare how many completed submissions came from each mode — a cheap first step toward the fuller comparison roadmap #24's instrumentation work is meant to cover.

#### Cross-bureau rationalization gate ("one Commerce")

Cross-bureau duplicate *detection* (`lib/similarity.ts` + `lib/crossBureauDuplicates.ts`, the "Possible duplicates" roll-up column and the submission detail "Similar use cases" panel) was purely informational — nothing made anyone act on "~20 of the same thing across the bureaus," the top concern from the DoC demo. `lib/rationalization.ts` adds the gate on top ([issue #52](https://github.com/mattshanklePA/launchpad-v0/issues/52)):

- **Clustering** — `clusterDuplicates()` groups submissions into connected components of the cross-bureau duplicate-match graph, where an edge is `lib/crossBureauDuplicates.ts`'s `isCrossBureauDuplicatePair` (same `ROLLUP_DUPLICATE_THRESHOLD` = 0.25 rule as the roll-up column: different bureau, not the same `lib/ombConsolidation.ts` category, `lib/similarity.ts` score at or above threshold). A cluster is only returned once it has 2+ members spanning 2+ bureaus. Cluster ids are deterministic — the lexicographically smallest member submission id — so they're stable across a demo reset against the golden seed. No-op (`[]`) for tenants without a bureau tier: `tenantHasBureauTier()` checks whether any `unit.options` entry declares `offices` (DoC-only, same signal `lib/tenant/index.ts`'s `getOrgNameForUnit` uses), so USPTO/DoW never see a cluster or a gate.
- **Decision** — a department/OS reviewer marks a cluster **consolidated** (picks a lead submission; the rest point at it) or **keep-separate** (not real duplicates / intentionally parallel) in the rationalization panel. The decision is persisted as `form_data.rationalization = { clusterId, decision, leadSubmissionId?, decidedBy, decidedAt }` on **every** cluster member (`lib/reviewWorkflow.ts`'s form-data-as-storage pattern — no schema change), written via `patchSubmissionFormData`. `lib/rationalization.ts` itself stays pure/I/O-free; `buildRationalizationPatch()` builds the patch object and callers apply it.
- **The gate** — `isRationalizationPending()`/`canApprove()`/`rationalizationBlockReason()` are the predicate: a submission that's a cluster member with no decision (or a decision recorded against a stale cluster id) is pending and blocks approval; a non-member is always approvable. Wired into the only reviewer approve path, `setSubmissionStatus(id, "approved")` in `components/submissions/submission-detail.tsx` — the Approve button is disabled with the reason shown inline, and `setStatus()` re-checks the gate before calling `setSubmissionStatus` so nothing else can bypass it. Deliberately computed against the **full, unscoped** submission set (not the viewer's `visibleSubmissions` roll-down that the "Similar use cases" panel uses) — a bureau-scoped reviewer approving their half of a cross-bureau duplicate must still be blocked even though they can't see the other bureau's half from their own view.
- **Surfacing** — `components/admin/rationalization-panel.tsx`, rendered in the Command Center's roll-up tab (`DepartmentDashboard`'s roll-up tab, `BureauDashboard`'s queue tab — see "Command Center landing dashboard" below) below the bureau roll-up, lists each cluster's members (title, bureau, link) and similarity, a decision control (pick-a-lead + Consolidate/Keep-separate buttons), and a roll-up summary ("N duplicate clusters · M rationalized"). Receives the same viewer-scoped `submissions` prop as `BureauRollup`, so it's meaningful for department/OS-level viewers and naturally empty for a bureau-scoped reviewer (consistent with the roll-up's existing scoping). The submission detail page also shows a compact per-submission cluster card (pending vs. decided, with the other members) next to the Approve button.

**Duplicate-rationalization vs. OMB-consolidation — two different axes, kept separate:** this gate (the *duplicate* axis) asks "is this the same effort as something in another bureau, and should we stop funding it twice?" `lib/ombConsolidation.ts`'s `determineConsolidation()` (the *OMB category* axis, previous section) asks a different question of a single submission — "does this match an OMB widely-used-commercial-AI category that can be reported once instead of per-bureau?" A submission can be in a rationalization cluster and independently be OMB-`Consolidated` or -`Individual`; the two never merge into one control, and `crossBureauDuplicates.ts`'s same-category exclusion keeps them from double-flagging the same pair in practice.

#### Bureau sign-off & department approval transparency

Approving or rejecting a use case (`setStatus` in `components/submissions/submission-detail.tsx`) used to be a bare status flip — no record of who signed off for the bureau or when, and no single view of sign-off progress across the dispersed bureaus for the Office of the Secretary. `lib/bureauSignoff.ts` adds that record and the transparency built on it ([issue #54](https://github.com/mattshanklePA/launchpad-v0/issues/54)), following `lib/rationalization.ts`'s pattern: a pure, I/O-free module with `getX`/`buildXPatch` helpers, persisted in `form_data` (no schema change) and applied via `patchSubmissionFormData`.

- **Bureau sign-off** — approving or rejecting now also records `form_data.bureauSignoff = { bureau, decision, signedOffByName, signedOffByEmail, signedOffAt }` in the same patch as the status change, gated on `tenantHasBureauTier()` (the same DoC-only signal `lib/rationalization.ts` uses, so USPTO/DoW's approve/reject flow is byte-for-byte unchanged). The submission detail view surfaces it as "Signed off by `<name>`, `<bureau>`, `<date>`" (or "Rejected by…").
- **Department approval transparency** — `approvalTransparency(submissions, viewer)` is the cross-bureau selector: per bureau, a count of signed-off/pending/rejected items plus a flat who/when item list. The hard limit lives in the selector, not the UI: it returns every bureau's data only when `hasDepartmentTransparency(viewer)` (an OS admin, `businessUnit === "os"`, or a department-level admin with no bureau assignment — the exact same gate `visibleSubmissions`'s roll-up uses, scoped to admins), and otherwise falls back to the viewer's own bureau via that same `visibleSubmissions` roll-down. `components/admin/approval-transparency.tsx` renders it below the bureau roll-up in the Command Center's roll-up/queue tab (see "Command Center landing dashboard" below) — passed the **full**, unscoped submission list (not the pre-scoped `submissions` prop `BureauRollup`/`RationalizationPanel` get) so the selector's own scoping is what a bureau-scoped reviewer's view depends on, not a second filter the UI has to get right.
- **Optional department-final-approval tier** — a second, independent confirmation on top of bureau sign-off (`form_data.departmentApproval = { decision, byName, byEmail, at }`), toggled per tenant via `TenantConfig.features.departmentFinalApproval` (`departmentFinalApprovalEnabled()`; on for DoC, unset elsewhere). Only rendered/actionable for `hasDepartmentTransparency(viewer)` once a bureau sign-off already exists — bureaus never see or perform it, and bureau sign-off is fully functional with the tier off.
- **Roll-up reporting** — `components/admin/bureau-rollup.tsx` adds a "Signed off" column (`X/Y` per bureau, plus a department total), gated on `tenantHasBureauTier()` like every other DoC-only column. `lib/approvalReport.ts` (reusing `lib/ombExport.ts`'s pattern, including the shared `lib/csv.ts` escaping helpers now used by both) builds a CSV — bureau, use case, status, signed-off-by, signed-off-at, department-approval — one row per submission; `app/api/export/approval/route.ts` streams it, linked from the Pipeline page's admin tools for `hasDepartmentTransparency` viewers only.
- The DoC seed (`lib/seedSubmissionsDoc.ts`) deliberately includes a signed-off-and-department-approved item (NIST), a rejected item with a recorded sign-off (MBDA), and an **already-approved item with no sign-off record** (ITA) — a stand-in for data from before this feature existed, showing up as "pending" in the transparency view/roll-up despite its status already being "approved." That gap is exactly the transparency problem this feature closes.

#### Field-config cascade (OMB → Department → Bureau)

Before this ([issue #57](https://github.com/mattshanklePA/launchpad-v0/issues/57)), `lib/fieldRegistry.ts`'s per-field on/off toggle was flat: a field was either `locked` (nobody can turn it off) or a plain optional toggle any admin could flip for every visitor. That's a compliance gap for DoC — OMB mandates a prescriptive field set every bureau must collect, the Department (Office of the Secretary) adds its own mandatory fields on top, and a bureau may add its own optional fields, but a bureau must never be able to remove what OMB or the Department mandated. The cascade adds that authority ordering on top of the existing toggle mechanism, additively:

- **`level` metadata** — `FieldDefinition.level` (`lib/fieldRegistry.ts`) is `"omb" | "department" | "bureau"`, defaulting to `"bureau"` when unset (`fieldLevel()`) so every pre-existing registry entry is unchanged unless explicitly marked. The OMB use-case-inventory fields are `level: "omb"` — reconciled against `docs/omb-2025-inventory-fields.md`, OMB's own published data dictionary for the 2025 consolidated inventory (34 fields: 25 base + 9 high-impact-only). Every field whose OMB-defined answer options are captured directly by the wizard is represented in `lib/fieldRegistry.ts` (annotated `#N` per that doc's row numbers) — including the four fields deferred by an earlier pass for lacking real option lists ([issue #63](https://github.com/mattshanklePA/launchpad-v0/issues/63)): `topicArea` (15 options), `aiClassification` (6 options), `demographicFeatures` (12 options, select-multiple), and `publicConsultationSteps` (6 options, select-multiple) — plus `hasPii` and `aiImpactAssessmentCompleted`, found missing during the same reconciliation ([issue #65](https://github.com/mattshanklePA/launchpad-v0/issues/65)). `id`, `use_case_name`, `agency_bureau`, `contact_email`, and `is_withheld` (doc rows #1-5) already have stand-ins collected elsewhere in the wizard (`useCaseTitle`, `submitterOffice`, `submitterEmail`, `isWithheld` — captures OMB's exact four-way `is_withheld` value set since [issue #116](https://github.com/mattshanklePA/launchpad-v0/issues/116)) rather than a duplicate `level: "omb"` entry. The four DoC-mandated AI risk questions (`involvesSensitiveData`, `aiDecisionalImpact`, `aiModelSourcing`, `aiHumanReview` — already `locked: true` before this change) are `level: "department"`, not `"omb"` — a distinct DoC/executive-order mandate, not one of the OMB inventory fields itself. Note `hasPii` (OMB, field #21) and `involvesSensitiveData` (DoC) overlap in subject but are separate mandates — both are kept. A `businessUnit` field optionally scopes a `level: "bureau"` field to one bureau (e.g. a future Census-only optional field) — no such field exists yet, but the mechanism supports it: adding one is a registry entry, not a code change.
- **Tenant gating — the reason USPTO/DoW are unaffected** — the OMB inventory fields stay `locked: false` in the registry itself (flipping that globally would have newly locked them for every tenant, since the registry is shared). Instead, every cascade function — `fieldsForBureau`, `canToggleField`, `isFieldEnabled`/`isFieldMandatory` (`lib/formConfig.ts`) — checks `tenantHasBureauTier()` (`lib/rationalization.ts`, the same DoC-only signal the rationalization gate and bureau sign-off already use) before applying `level` at all. On a flat tenant, `level` is ignored entirely and behavior is byte-for-byte what it was before this issue; on DoC, `level: "omb"`/`"department"` fields become non-togglable and appear for every bureau regardless of the stored `enabled` map.
- **`fieldsForBureau(businessUnit)`** (`lib/fieldRegistry.ts`) is the single place that resolves "which fields apply to this bureau": every OMB/department field, plus the general unscoped optional pool (today's shared toggle set), plus any field scoped to `businessUnit` — never another bureau's scoped field. Both the wizard (`isFieldEnabled`/`useFieldVisibility` in `lib/formConfig.ts`, now taking an optional `businessUnit` — every wizard step component passes `formData.submitterOffice`) and the admin toggle UI (`components/admin/form-config-panel.tsx`, scoped to `getSession()?.businessUnit`) filter through it, so they can't drift apart.
- **`canToggleField(field, viewer, opts)`** is the permission predicate: locked fields are never togglable; on a bureau-tier tenant, `omb`/`department` fields are never togglable by anyone; a `businessUnit`-scoped field is togglable only by that bureau's viewer or a department-level viewer (`isDepartmentLevelViewer` — an `os`-bureau or no-bureau-assignment viewer, the same shape `hasDepartmentTransparency` in `lib/bureauSignoff.ts` uses); the general optional pool stays togglable by any admin, matching pre-cascade behavior.
- **Admin-promoted "mandatory for all bureaus"** — an OS/department admin can also promote an ordinary optional `level: "bureau"` field to mandatory for every bureau without a registry change, via `setFieldMandatory()`/`FormConfig.mandatory` (`lib/formConfig.ts`), gated by `canMarkFieldMandatory()`. This is a second jsonb column on `form_config` (`db/migrations/doc/0002_field_cascade_mandatory.sql`, additive — USPTO/DoW never run it and never send a `mandatory` value on `PUT /api/form-config`, so their deployments work unmigrated). Once set, `isFieldMandatory()` treats the field exactly like an OMB/department field — it appears for every bureau and only a department-level viewer can un-mandate it.
- **Admin UI** (`components/admin/form-config-panel.tsx`) — an OMB/department/mandatory field renders on and disabled with a badge (OMB / Department / "Mandatory (all bureaus)") and a one-line hint ("Required by OMB — mandatory for every bureau, cannot be turned off."); a bureau-scoped field carries a "`<Bureau>` only" badge and is disabled outside that bureau; a department-level viewer sees a "Mark mandatory for all bureaus" control on ordinary optional fields. Header counts (`X enabled`, `Y hidden`, `Z locked / mandatory`) are scoped to `fieldsForBureau(viewer's bureau)`, not the full registry, so a bureau admin's summary reflects only what they can see.
- **Full reconciliation (issue #65)** — all 34 fields in `docs/omb-2025-inventory-fields.md`'s data dictionary are now represented (directly, or via a stand-in noted above), each with OMB's exact answer-option list rather than a placeholder Yes/No. `is_high_impact` is the doc's real three-way choice (not binary), with its conditional `HI_justification` sub-field; all 9 high-impact-only fields (#26-34) carry their real multi-value option sets — Yes/In-progress/CAIO-waived, not just Yes/No — and every `showWhen` predicate matches the doc's "Required when" column, including compounding a parent-answer gate with a stage gate where the doc requires both (`atoSystemName`, `systemSourceVendorName`). **`docs/omb-field-mapping.md`** consolidates this into a single table — all 34 OMB fields, the `FormData` field that supplies each one, and a kept/renamed/added/stand-in status — plus the LaunchPad risk-question mapping (`involvesSensitiveData`, `aiDecisionalImpact`, `aiModelSourcing`, `aiHumanReview`) and the `has_pii`/`involvesSensitiveData` overlap.

#### NIST AI RMF mapping + `computeRmfProfile`

**`docs/nist-rmf-mapping.md`** ([Roadmap #22](https://github.com/mattshanklePA/launchpad-v0/issues/130), ClickUp 868kcr3u5) specifies the NIST AI Risk Management Framework governance layer as a **lens** over the existing OMB/DoC fields above — not new intake. It maps each of the four RMF functions (Govern / Map / Measure / Manage) to the `FormData` fields and determination modules that already evidence it (e.g. Govern <- `reviewStatus`/`bureauSignoff`/`departmentApproval`, `hasATO`, `isWithheld`; Measure/Manage <- the 9 `hi_*` high-impact risk-management fields), a deterministic per-function status rubric, and an overall RMF profile rollup mirroring `lib/riskProfile.ts`'s `computeRiskProfile` cascade — a separate signal from that EO risk badge, not a replacement for it. It also lists the small number of DoC AI Use Case Tracker columns (disseminates-to-public, scalable, data readiness, base platform/model) with no existing LaunchPad signal; the first two (`disseminatesToPublic`, `scalable`) are added as intake fields in story 4 below (`lib/fieldRegistry.ts`, `level: "department"`) and folded into `computeRmfProfile`'s Map rubric itself (a submission counts them as answered on either a "yes" or a "no"); data readiness and base platform/model remain future new-field candidates.

**`lib/nistRmf.ts`** (`computeRmfProfile`) implements that spec's §5/§6 rubric literally — pure, deterministic, no I/O, same determination-module style as `determineHighImpact`/`determineReportability`: it reads the mapped fields directly (the single source of truth) rather than recomputing a second copy of an existing determination. For each function it returns a `RmfFunctionResult` (`status: "covered" | "partial" | "gap" | "not_yet_applicable"` + `reasons`); Measure and Manage share the same `highImpact === "high_impact" && stageOfDevelopment === "deployed"` applicability gate as `lib/fieldRegistry.ts`'s `highImpactAndDeployed` `showWhen` predicate, so a pre-deployment or non-high-impact use case reports `not_yet_applicable` rather than a false gap. Govern additionally takes an optional `tenant` (default `getTenant()`) since its "approved" bar includes department approval only once `departmentFinalApprovalEnabled(tenant)` is on (DoC), mirroring `lib/bureauSignoff.ts`'s own tenant-gated pattern; `bureauSignoff`/`departmentApproval` aren't part of `FormData` itself, so callers with a `Submission` pass `getBureauSignoff(s)`/`getDepartmentApproval(s)` through as extra fields on the input. The overall `RmfProfile` (`overall: "on_track" | "attention" | "at_risk" | "unknown"`, `rationale`, `flags`) follows §6's cascade: `unknown` when Map itself is `not_yet_applicable` (nothing submitted yet); `at_risk` on any function `gap`; `attention` on any `partial`, or on a high-impact-but-pre-deployment use case whose Measure/Manage are still `not_yet_applicable` (flagged early rather than only once overdue); else `on_track`. `rmfBadgeClass`/`rmfFunctionStatusBadgeClass` mirror `riskBadgeClass`'s color-token style (`lib/nistRmf.test.ts` covers covered/partial/gap per function and the rollup cascade).

**At-submission scoring + reviewer confirm/override (`lib/rmfProfileReview.ts`, Roadmap #22 story 4)** — a computed governance profile shouldn't be silently authoritative, so the profile is snapshotted once, at submission (`buildRmfProfileSnapshotPatch`, merged into the saved `form_data` by `lib/adapters/default/supabaseStore.ts`'s `saveSubmission` alongside the existing reviewer auto-assignment), and a reviewer explicitly confirms or overrides it (`buildRmfProfileReviewPatch`, applied via the existing `patchSubmissionFormData`) — the same propose-then-confirm relationship `lib/ombAutofill.ts`'s AI-proposed fields have to the submitter's confirmation, and the same get/build-patch shape as `lib/bureauSignoff.ts` (`rmfProfileSnapshot`/`rmfProfileReview` likewise aren't part of `FormData` itself — read via casts). `resolveRmfProfile(submission, tenant)` is the single place both UI surfaces read from: it prefers the stored snapshot, falling back to a fresh `computeRmfProfile` call for submissions saved before this feature existed (older/seeded data) — never a second rubric — and resolves `effectiveOverall` (the reviewer's overridden level once one is recorded, else the computed `overall`) plus `isProposal` (true until a reviewer has acted).

Both surfaces are gated on the tenant `rmf` feature flag (on for DoC only, mirroring `aiHubExport`'s tenant-gated pattern) so USPTO/DoW are unaffected. The submission detail view (`components/submissions/submission-detail.tsx`) renders a "NIST AI RMF" card below the existing "Risk profile" card — the overall level as a badge (`RMF_OVERALL_LABELS`/`rmfBadgeClass`, tagged "proposed · awaiting reviewer" until reviewed) plus a per-function status chip and reasons list for Govern/Map/Measure/Manage (`RMF_FUNCTION_ORDER`), computed via `resolveRmfProfile(sub, tenant)`. A reviewer sees Confirm/Override controls (mirroring the existing high-impact reviewer-determination buttons on the same page); overriding picks one of the four overall levels and records an optional reason, persisted as `rmfProfileReview` (who/when/decision/proposed vs. overridden level). Decision Center (`components/admin/decision-center.tsx`) badges each `DecisionCard` with the same `resolveRmfProfile` result (marking `(proposed)` until reviewed), alongside the existing `computeRiskProfile` risk badge — a separate signal, not a replacement for it.

#### Command Center landing dashboard

`/home` — the route every signed-in user lands on — is the Command Center: a landing dashboard that gives a viewer a summary view scoped to their place in the org, instead of dropping them straight on the full pipeline. `app/home/page.tsx` resolves `getDashboardScope(session)` and dispatches to one of three scoped screens: `DepartmentDashboard` (department/OS scope), `BureauDashboard` (bureau/office scope), or `PersonalDashboard` (personal scope). Everything is derived from the same libs the pipeline/roll-up/OMB surfaces already use — no new data model.

**Scope model, i.e. the role-to-scope map (`lib/dashboard/scope.ts`)** — `getDashboardScope(session)` returns a `DashboardScope` (`"department" | "bureau" | "office" | "personal"`, carrying `businessUnit`/`office`/`email` as applicable), resolved by this rule (the *exact same* roll-down rule `visibleSubmissions`, `lib/reviewWorkflow.ts`, already applies, so a Command Center card can never disagree with the pipeline/roll-up views):

| Viewer | Scope |
| --- | --- |
| Submitter | `personal` |
| Reviewer, or admin with `businessUnit !== "os"` and no `office` | `bureau` |
| Reviewer or admin with `businessUnit !== "os"` and an `office` | `office` |
| Office of the Secretary (`businessUnit === "os"`), or any viewer with no `businessUnit` | `department` |

`getHierarchy()` exposes the full department → bureau → office tree from `getTenant().unit.options`; `getScopeSubtree()` returns the bureau/office constraint a scope implies (`[]` for `department`/`personal`); `isLevelAllowed(scope, level)` says whether a scope is broad enough to render a card aggregated at a given level (department is broadest, personal narrowest). Like `visibleSubmissions`, this is a view-model convenience, not a security boundary.

**Metrics adapter (`lib/dashboard/metrics.ts`)** — pure functions that take a `DashboardScope` plus the app's cached submissions and return typed Command Center card values, reusing rather than reimplementing each domain module: pipeline status counts (`getStatus`/`STATUS_ORDER`, `lib/reviewWorkflow.ts`), a readiness-score distribution (`formData.readinessScore`), a recommended-high-impact count (`determineHighImpact`, `lib/highImpactDetermination.ts` — the manual-plus-inferred recommendation, not the bare self-reported flag), an awaiting-bureau-sign-off count (`getBureauSignoff`, `lib/bureauSignoff.ts` — the "approved but not yet signed off" gap, always 0 for a tenant with no bureau tier), an OMB reportability + consolidated/individual breakdown (`determineReportability`/`determineConsolidation`), a cross-bureau duplicate-cluster summary (`clusterDuplicates`/`isRationalizationPending`, `lib/rationalization.ts` — clustering deliberately runs over the *full* unscoped submission set per that module's own rule, then is filtered down to clusters touching the scope), and a NIST AI RMF overall-level rollup (`rmfRollupSummary`, counts by `on_track`/`attention`/`at_risk`/`unknown` — built on `resolveRmfProfile`, `lib/rmfProfileReview.ts`, so a reviewer's confirmed/overridden level counts here exactly as Decision Center and the submission detail page badge it, not the raw `computeRmfProfile` proposal alone). Per-bureau roll-up rows are built the same way `components/admin/bureau-rollup.tsx` aggregates (one row per bureau present in scope, via `getStatus`/`getBusinessUnit`/`STATUS_ORDER`); per-office roll-up rows for the scope's own bureau delegate directly to `officeRollupRows` (`lib/officeRollup.ts`). Every card is built on top of `scopedSubmissions(scope, submissions)`, which mirrors `visibleSubmissions`'s filter predicate keyed off a `DashboardScope` instead of a `{ role, businessUnit, office }` viewer — so a bureau/office-scoped card can never count a submission outside that scope. `getDashboardMetrics(scope, submissions, tenant)` computes every card in one pass.

**Shell components, including the CC-STYLE restyle (`components/dashboard/`)** — every component takes typed props and does no fetching. `dashboard-shell.tsx` (`DashboardShell`) is the persistent frame every scoped view mounts into: a left sidebar (`SidebarProvider`/`Sidebar`/`SidebarInset`, `components/ui/sidebar.tsx` — a trimmed sidebar primitive with a desktop icon-collapse rail plus an off-canvas panel under `1024px`, state persisted to `localStorage`, styled off the app's `--sidebar-*` CSS tokens) + a sticky header (`SidebarTrigger`, a scope breadcrumb, a Home link, and the same session/sign-out menu the global `Header` shows elsewhere) + a main content area. The sidebar carries an "Organization" group (`EntityTree`, below, restyled into the sidebar's own `SidebarMenu`/`SidebarMenuSub` components so Department → Bureau → Office drill-down reads as native sidebar navigation), a "Workspace" group (Submit an idea, always; Decision Center, admin/reviewer only), and an "Admin" group (form configuration, user management, demo data, and the OMB/approval CSV exports — admin only, the approval export additionally gated on `tenantHasBureauTier()` + `hasDepartmentTransparency`). Every dashboard panel renders through the shared `Card`/`CardHeader`/`CardTitle`/`CardContent` primitives (`components/ui/card.tsx`), so panels follow the `.dark` theme (`bg-card text-card-foreground`) rather than a hardcoded `bg-white`. The content-area building blocks the three scoped views assemble from: `kpi-card.tsx` (`KpiCard`/`KpiCardGrid`, a generic `label`/`value`/`delta`/`status` grid, up to 6 columns, each card hover/click-interactive when a drill-down is passed — see the KPI drill-down entry below), `health-gauge.tsx` (`HealthGauge`, a 0-100 scalar rendered as a color-banded semicircular arc), `entity-tree.tsx` (`EntityTree`, a lightweight custom Department → Bureau → Office nav driven by `getHierarchy()`'s `OrgHierarchy` — no external tree library; a bureau with no `offices` renders as a leaf, so USPTO/DoW show bureaus only while DoC expands into offices), `charts/pipeline-status-chart.tsx` and `charts/readiness-distribution-chart.tsx` (recharts panels typed directly against `PipelineStatusCard`/`ReadinessDistributionCard`, using the app's `--chart-*` CSS variables so they follow light/dark), `queue-board.tsx` (`QueueBoard`, a per-status Kanban board of the scope's submissions), and `action-center.tsx` (the live Action Center, below). Each component's non-trivial pure logic (band thresholds, severity ordering, selection matching, card → chart-row mapping) is split into a sibling `*-data.ts` module with its own unit tests, the same pattern `lib/officeRollup.ts`/`components/admin/office-rollup.tsx` already established, so the logic is tested without rendering React.

**The three scoped views** — `DepartmentDashboard` (`department-dashboard.tsx`) is the department/OS-scoped view, ordered worklist-first (UX #4): the header, an admin-only dismissible `OrientationBanner` (below), a one-line `WorklistSummary` ("Today: N items need you", below), a `Tabs` block (Action Center, the default tab; Overview — pipeline-by-status chart, health gauge, readiness distribution; and `{tenant.unit.label} roll-up` — the existing `BureauRollup`, which itself renders `OfficeRollup` on expand, plus `RationalizationPanel` and `ApprovalTransparency`), and — last, as a visually thinner band rather than the page's first impression — the KPI row under a "Key metrics" heading. Selecting a bureau (then an office where the tenant has one) in `EntityTree` updates local state; `resolveDrillScope` (`department-dashboard-data.ts`) turns that into a narrower `DashboardScope` fed back through `getDashboardMetrics`, so every card recomputes for the selected node with no separate per-card fetch — a selection outside what the viewer's base scope is broad enough to see (`isLevelAllowed`) is ignored, so tree selection can never escape the viewer's own roll-down. Sign-off and cross-bureau-duplicate KPI/Action-Center items only appear for bureau-tier tenants (`tenantHasBureauTier`, DoC); an "RMF at risk" KPI card only appears for tenants with `features.rmf` on (DoC, `buildKpiCards`'s `rmfEnabled` param — the same gate `submission-detail.tsx`/`decision-center.tsx` use for their own RMF surfaces); pipeline size, readiness, recommended high-impact, and OMB reportability render for every tenant. Pure logic (`resolveDrillScope`, `scopeLabel`, `buildKpiCards`, `buildActionItems`, `computeHealthScore` — a 0-100 scalar weighting ready submissions fully and needs-work submissions at half — and `worklistSummaryLabel`, below) lives in `department-dashboard-data.ts`, unit-tested without rendering React. No change to `lib/dashboard/metrics.ts`'s metric logic — this pass is layout, tooltips, and orientation copy only.

`BureauDashboard` (`bureau-dashboard.tsx`) is the reviewer/bureau analog, computed for a `bureau`/`office` scope instead of `department`: it calls the identical `getDashboardMetrics`/`getDashboardActions`/`scopedSubmissions` and the identical `buildKpiCards`/`buildActionItems`/`computeHealthScore` `DepartmentDashboard` uses (already scope-agnostic), follows the same worklist-first order (`OrientationBanner`, `WorklistSummary`, then the Action Center-first `Tabs`, then the "Key metrics" KPI row last), plus its own Queue tab (`QueueBoard`, a per-status Kanban worklist, and an "Office breakdown" panel — `OfficeRollup` — when the bureau declares offices). Because `EntityTree`'s underlying hierarchy and `resolveDrillScope` only check whether a selection's *level* is broad enough (`isLevelAllowed`), not whether it matches the viewer's own bureau, `bureau-dashboard-data.ts` adds bureau-safe replacements: `bureauHierarchy(scope, tenant)` restricts the sidebar tree to just the viewer's own bureau (and its offices), and `resolveBureauDrillScope(base, selection)` re-checks `selection.businessUnit === base.businessUnit`, so a bureau/office-scoped viewer can never drill into another bureau's data.

`PersonalDashboard` (`personal-dashboard.tsx`) is the submitter-scoped view: client-side draft detection (`detectDraft()`, reading the signed-in user's scoped `aid-form-data:<userId>` key via `lib/draftStorage.ts`), a prominent "Start a new idea" action (`/submit`), and an "Action needed" section listing the submitter's own `needs_info` submissions with the latest reviewer comment inline, sourced via `scopedSubmissions(scope, submissions)` so this list can never disagree with what `getDashboardScope`/`visibleSubmissions` resolve for the same viewer elsewhere in the app. It passes `hierarchy={{ bureaus: [] }}` to `DashboardShell` (no org tree to browse) and skips the KPI grid/Action Center entirely — those cards are reviewer/admin-facing concepts a submitter has no use for.

Across all three views, `components/dashboard/dashboard-workspace-links.tsx` (`DecisionCenterLink`, `AdminToolsSection`) renders the Decision Center link and the admin-only tools menu (form configuration, user management, demo data, OMB/approval CSV exports, as a compact header dropdown rather than a grid, so it doesn't outweigh the Action Center/pipeline content below — the same links are also in the sidebar's "Admin" group) inside `DepartmentDashboard` and `BureauDashboard` (not `PersonalDashboard` — reviewer/admin-only concepts).

**Worklist-first orientation (UX #4, `worklist-summary.tsx` + `orientation-banner.tsx`)** — two small presentational pieces `DepartmentDashboard`/`BureauDashboard` render above their `Tabs`, so an admin's first read is "what needs me," not the metrics wall the KPI row used to be. `WorklistSummary` renders `worklistSummaryLabel(actionItems)` (`department-dashboard-data.ts`, unit-tested) as a one-line "Today: N items need you" (or a calm "nothing needs you right now" once the list is empty) off the exact same `actionItems` array the Action Center itself lists below, so the headline can never disagree with the list. `OrientationBanner` is a dismissible explainer of how a use case moves through review (`Submitted → In review → Approved → [Bureau sign-off →] OMB reportable`, the bracketed stage only for bureau-tier tenants), shown only to `hasAdminAccess` viewers; it persists its dismissal via the same `usePersistentDisclosure` localStorage hook the wizard's optional-detail disclosures use (`hooks/use-persistent-disclosure.ts`), so it reads as first-run — shown until dismissed once, not on every visit — without a new storage mechanism. Tenant-neutral: both read off `bureauTier`/`actionItems` already computed for the KPI row, no tenant-specific copy.

**KPI drill-down data layer (Roadmap #26, `lib/dashboard/drilldown.ts`)** — `getKpiDrilldown(scope, submissions, tenant)` answers "which submissions make up this count" for each KPI card, so the hover/click UI below can list the use cases behind a number without a second data model. Every predicate is imported straight from `lib/dashboard/metrics.ts` (exporting `readinessBucket` for this reuse) rather than re-implemented, so a drill-down list's length always equals its card's count: `pipeline` <-> `pipelineStatusCounts(...).total` (every `scopedSubmissions` row), `readiness` <-> `readinessDistribution(...).ready` (`readinessBucket(s) === "ready"`), `high-impact` <-> `highImpactCount(...).count` (`determineHighImpact(s.formData).recommendation === "yes"`), `omb-reportable` <-> `ombReportabilitySummary(...).reportable` (`determineReportability(s.formData).status === "reportable"`), `signoff` <-> `awaitingSignoff(...).count` (`getStatus(s) === "approved" && !getBureauSignoff(s)`, `[]` for tenants with no bureau tier), `duplicates` <-> `crossBureauDuplicatesSummary(...).clusterCount` (`clusterDuplicates`'s in-scope clusters — clustering itself still runs over the full unscoped submission set per that module's own rule, then only clusters with a member in this scope are returned), and `rmf` <-> `rmfRollupSummary(...).at_risk` (`resolveRmfProfile(s, tenant).effectiveOverall === "at_risk"`, same authoritative-level source the rollup card uses). Each non-cluster item is a compact `KpiDrilldownItem` (`id`, `title` — `formData.useCaseTitle` or "Untitled idea", `bureau`/`bureauLabel`, `stage` — `STATUS_LABEL[getStatus(s)]`, and a card-specific `cardField`: the pipeline status label, the readiness bucket, `determineHighImpact`'s rationale, the reportability reason plus `determineConsolidation` status, a sign-off note, or the resolved RMF profile's rationale); `duplicates` returns cluster-shaped `DuplicateClusterDrilldownItem`s instead (adds `memberIds`, with `bureau`/`bureauLabel`/`cardField` describing the cluster rather than a single submission, and `id` set to the cluster's lead submission's id). Pure and tenant-neutral, like every other card in `lib/dashboard/metrics.ts`.

**KPI card hover preview + click-through drill-down (Roadmap #26, `kpi-card.tsx`)** — the UI layer over the drill-down data above. `DepartmentDashboard`/`BureauDashboard` compute `getKpiDrilldown(scope, submissions, tenant)` alongside their existing `buildKpiCards(metrics, bureauTier)` call and pass both into `KpiCardGrid` as `cards`/`drilldown`; `KpiCardGrid` looks each card's `id` up in the drill-down (`kpiDrilldownEntriesFor`, `components/dashboard/kpi-card-data.ts`) and passes the matching list to `KpiCard` as `items`. Every `KpiCard` is a `Card` with a fixed two-part layout: a `KpiCardLabel` row up top (the label, plus a `GlossaryTerm` "?" tooltip when the card carries a `glossary` key — see below) and a `KpiCardBody` below it (value, optional `subtitle`, delta). A `KpiCard` given no `items` prop (any caller/test still passing just `label`/`value`/`delta`/`status`) renders both parts as static text. A `KpiCard` given `items` wraps only `KpiCardBody` — not the label row — in a real `<button>`, itself wrapped in both a `Dialog` (`components/ui/dialog.tsx`) and a `HoverCard` (`components/ui/hover-card.tsx`), the two shadcn/Radix primitives added for this feature: clicking (or Enter/Space, or a touch tap) opens the `Dialog` (widened to `sm:max-w-2xl`, `overflow-x-hidden` plus `min-w-0` on its list so the grid-child sizing quirk that used to clip the row's action link can't recur), listing every item as a `DrilldownRow` with a truncated, hover-tooltipped title, `presentCardField(item)` (`kpi-card-data.ts`) splitting the entry's free-form `cardField` into a compact classification `Badge` (e.g. Individual/Consolidated) plus an optional one-line descriptor, and an "Open submission"/"Open cluster" link — always fully visible, wrapping below the row on narrow widths rather than clipping — to `kpiDrilldownEntryHref(item)` (`/submissions/{id}`, reusing the `queue-board.tsx`/`rationalization-panel.tsx` link pattern); hovering or keyboard-focusing the button additionally opens the `HoverCard`, previewing up to `KPI_HOVER_PREVIEW_LIMIT` (4) compact "baseball cards" (title, bureau, stage, card-specific field) with a "+N more" line once the list is longer, from `previewKpiDrilldownEntries`/`kpiDrilldownOverflowCount`. The `Dialog` click path is the accessible primary: because it's a native button (labeled via `aria-label` with the card's `label`, since the visible label text itself sits outside it), keyboard and touch users reach the full list without ever hovering, satisfying the 508 guardrail that the pointer-only `HoverCard` (Radix never fires it on touch) is an enhancement, not the only route to any information. `duplicates` needs no special-case branch in the component itself — `isDuplicateClusterEntry` (a `"memberIds" in item` type guard) drives a cluster-only "N submissions" badge and the "Open cluster" link label, and since a `DuplicateClusterDrilldownItem`'s `id` is already its lead submission's id, `kpiDrilldownEntryHref` resolves every entry, cluster or not, to the same `/submissions/{id}` route — landing on a cluster's lead opens `submission-detail.tsx`'s own cross-bureau rationalization section for that cluster. An empty `items` list (count 0) still opens the `Dialog` — the accessible path always works — showing "Nothing here right now." instead of any rows, and suppresses the `HoverCardContent` entirely (nothing to preview). Tenant-neutral like the rest of the KPI row: `signoff`/`duplicates` simply aren't in `cards` for non-bureau-tier tenants (USPTO/DoW), so those two `KpiCard`s never render for them.

**KPI glossary tooltips + subtitles (UX #4)** — `buildKpiCards` (`department-dashboard-data.ts`) attaches a `glossary` key (`lib/glossary.ts`) plus a short always-visible `subtitle` to every jargon KPI label: `pipeline` (`inPipeline`), `readiness` (`readinessReady`), `omb-reportable` (`ombReportability`, reused from the reviewer detail view), `signoff` (`awaitingBureauSignOff`, reused), `duplicates` (`crossBureauRationalization`, reused), and `rmf` (`rmfAtRisk`). `inPipeline`/`readinessReady`/`rmfAtRisk` are new glossary entries added for this pass; the rest already existed for `submission-detail.tsx`/`decision-header.tsx` and are simply pointed at from a second place, so a term's definition never forks between the two screens. `KpiCardLabel` wraps the label text in `GlossaryTerm` only when `glossary` is set — the label row deliberately sits above, and outside, the card's click-through button described above, because `GlossaryTerm` renders its own `<button>` and HTML doesn't allow nesting one interactive control inside another. The `subtitle` (e.g. "Total use cases in review", "May be the same effort, built twice") is the always-visible explanation for anyone who won't hover or long-press the tooltip; the "?" tooltip adds the fuller glossary definition on top of it. `high-impact` keeps no `glossary`/`subtitle` — "Recommended high-impact" isn't jargon in the same way the other six labels are, and UX #4's guardrail scoped the tooltip pass to exactly those six.

**Live Action Center** — `lib/dashboard/actions.ts` (`getDashboardActions`) derives real, per-submission action items, scoped via `scopedSubmissions` so a bureau/office-scoped reviewer's action list can never include another bureau's item: `needs_info` (submissions waiting on a reply from the submitter), `unassigned` (active submissions with no reviewer on file, via `getAssigneeEmail`), and `signoff_nudge` (approved submissions with no recorded `bureauSignoff`, bureau-tier tenants only). The recipient guard, `canAutoSend`, preserves the app's existing boundary that there is no channel to notify a submitter outside the product itself (no email/Teams adapter; the Slack webhook posts to one internal team channel): a `needs_info` action's `canAutoSend` is always `false` (reaching the submitter still goes through the existing in-app Request-info path); an `unassigned` action is `false` until an admin assigns a reviewer; a `signoff_nudge` action is `true` only when the bureau's on-file reviewer (`assigneeForBusinessUnit`) is actually on file. `buildNotificationBatch(actions)` joins only the `canAutoSend` messages from a batch and returns `null` when nothing may auto-send, so a caller can tell "drafted, not sent" apart from "sent to N." `app/dashboard-actions.ts` (`sendDashboardActionNotification`, a server action) calls `buildNotificationBatch` and, only if it returns non-null, `getNotifier().send(...)` — the existing `Notifier` port (`lib/notifier.ts` → `lib/adapters/default/slackNotifier.ts` → `lib/slackWebhook.ts`). `department-dashboard-data.ts`'s `buildActionItems` wires this server action into two `ActionItem`s — sign-off nudge and request info — plus a third, informational-only unassigned item with no button. `ActionCenter` (`components/dashboard/action-center.tsx`) supports `ActionItem.onAction: () => Promise<ActionOutcome>` (`action-center-data.ts`): a per-item pending spinner while the action resolves, then a toast — "Notification sent" or "Drafted, not sent" (a thrown error is the only failure/destructive toast).

**Controls that reflect the record (ES2-12)** — two places where a control said something the record did not. An `ActionItem` now carries an optional `drilldown: { label, items }` (`action-center-data.ts`): its button is a `DialogTrigger` opening `DrilldownDialogContent` (exported from `components/dashboard/kpi-card.tsx`, the same dialog body the KPI cards use), so a button lands the reviewer on the records behind the count it sits next to rather than a second, divergent list. `buildActionItems` takes the caller's `KpiDrilldown` as a fifth argument and attaches it to the rationalization, reportability-review, unassigned, and needs-info items; the sign-off nudge keeps `onAction` (it is the one action `canAutoSend` can really send), and the retired needs-info wiring lost nothing, since `canAutoSend` is always false for that kind. `drilldown` and `onAction` are alternatives, never a pair, and an item with neither renders **no button at all** — a disabled "Review" told the reviewer there was something to click when nothing was wired. On the reviewer detail side, the Disposition checklist row now lives in `components/submissions/disposition-controls.tsx`, whose pure `dispositionButtonVariant(action, status)` gives the button matching the recorded status the `default` variant and the other `outline` — the rule the High-impact determination control already followed. Both buttons stay enabled either way, so a reviewer can still reverse a decision; what changes is which one reads as current.

**Dashboard subtraction (ES2-15)** — an optional `TenantConfig.dashboardKpiCardIds` selects *and orders* the KPI strip: `buildKpiCards` assembles every card as before, then returns only the ids in that list, in that order. Unset (uspto, doc, dow) means every card the tenant qualifies for renders, unchanged; es2 pins `pipeline`, `duplicates`, `high-impact`, `rmf`. Filtering is display-only — `getKpiDrilldown` and `buildActionItems` are untouched, so the Action Center rows and roll-up columns for an unrendered card keep their lists. On all four tenants the gauge card is titled "Decision readiness" with a `CardDescription` naming its weighting (ready in full, needs-work at half — `computeHealthScore` itself is unchanged), and `bureau-rollup.tsx` carries a legend under the table naming what its red, amber and purple badges mean.

**Guardrails** — every card and nav item routes through the same `getDashboardScope`/`scopedSubmissions`/`visibleSubmissions` roll-down described above, so who-sees-what is identical to the rest of the app; the sign-off, cross-bureau-duplicate, and office-breakdown surfaces are gated on `tenantHasBureauTier()` so USPTO/DoW render the same dashboard shell with those DoC-only cards absent; every label comes from `getTenant()`. Verified tenant-neutral against both USPTO (no office tier) and DoC (full three-level org tree).

#### Shared compliance glossary & tooltip layer

UX simplification decision: a compliance term (OMB reportability, cross-bureau rationalization, high-impact determination, NIST AI RMF, etc.) always stays on screen in its formal form — nothing gets renamed — but can carry a plain-language explanation in place, instead of leaving that explanation to only one screen. Before this, the only inline explanation anywhere was the wizard's `FieldRequirementBadge` tooltip (issue #60); the reviewer detail view and the Command Center dashboard had none.

`lib/glossary.ts` is the single term -> definition map (`GLOSSARY: Record<GlossaryTermKey, { term, definition }>`), seeded with the starter set: cross-bureau rationalization, OMB reportability, consolidated/individual reporting, high-impact determination, NIST AI RMF (Govern/Map/Measure/Manage), covered/partial/gap, token-overlap match, awaiting bureau sign-off, and advisory. Definitions are written tenant-neutral (no org names) so the same entry reads correctly for USPTO, DoW, and DoC. `components/launchpad/glossary-term.tsx`'s `GlossaryTerm` component is the one reusable renderer: it looks up a `GlossaryTermKey` and wraps its label (the formal term by default, or `children` when a caller wants different visible text) in a Radix `Tooltip` (`components/ui/tooltip.tsx`, the same primitive `FieldRequirementBadge` already uses) with a small "?" (`HelpCircle`) affordance — focusable and keyboard-accessible (opens on focus, dismissible with Esc) since it reuses Radix's own trigger/content behavior rather than a custom hover-only implementation. Originally introduced with one demo usage (the wizard's Feasibility & Security step, since removed from intake — issue #162 — and now `components/submissions/governance-capture-panel.tsx`'s high-impact question); the reviewer detail view is now wired in too (below). The Command Center dashboard remains separate follow-on work.

#### Reviewer detail redesign: decision header, guided checklist, progressive disclosure

UX simplification decision ([issue #145](https://github.com/mattshanklePA/launchpad-v0/issues/145)): before this, `components/submissions/submission-detail.tsx` opened into 10+ co-equal cards and asked the reviewer for up to 5 decisions (dispose, high-impact determination, RMF confirm/override, cross-bureau rationalization, department final approval) with no order and no guidance — the same page a submitter lands on to check status, just with more controls. The redesign restructures the reviewer's view into three zones, presentation/IA only — no change to any underlying determination, action, or persisted data shape, and the advisory-vs-decide distinction (the assistant recommends, the reviewer decides) is preserved throughout.

- **Zone 1 — Decision header** (`components/submissions/decision-header.tsx`, reviewer/admin only). Surfaces `{tenant.assistantName}`'s rolled-up recommendation (`assistReviewer`'s `verdict`/`suggestedDisposition`, unchanged), a single "what's blocking approval" line, and one primary action. The blocking line and the primary action are both derived in `submission-detail.tsx` from data every other part of the page already computes — nothing new is calculated: `blockReason` (`lib/rationalization.ts`'s existing hard gate on `Approve`) takes priority when present; otherwise, if the assistant's `suggestedDisposition` isn't `"approve"`, that becomes the blocking reason (the reviewer is routed to the checklist rather than a one-click approve, though the individual Approve/Reject/Request-info actions still exist in the checklist's first item — nothing is removed, just de-emphasized as *primary*); otherwise there's nothing blocking and the primary action is "Approve as recommended", calling the same `setStatus("approved")` the page always has. The assistant's full strengths/gaps analysis (previously always-visible) collapses behind a "See `{assistantName}`'s full analysis" toggle in this same zone — progressive disclosure applied to the AI read itself, not just the compliance data.
- **Zone 2 — Guided decision checklist** (`components/submissions/checklist-item.tsx`'s `ChecklistItem`, reviewer/admin only). An ordered, numbered `<ol>` of only the items that need the reviewer, each status-tagged and actionable inline, numbered sequentially over only the items that actually render for this submission (e.g. a tenant without the `rmf` flag never sees a gap in the numbering): (1) Disposition — the existing Approve/Request info/Reject buttons, unchanged; (2) High-impact determination — the existing recommendation + reviewer buttons, unchanged; (3) NIST AI RMF confirm/override — the existing overall badge + Confirm/Override controls (the full Govern/Map/Measure/Manage breakdown moves to Zone 3, see below), gated on `tenant.features.rmf` as before; (4) Cross-bureau rationalization — same cluster/member data as before, but the block reason is no longer prose pointing at "the Rationalization panel on the Pipeline page": a department/OS viewer (`hasDepartmentTransparency`) gets the actual decide UI inline, by embedding the existing `components/admin/rationalization-panel.tsx` scoped to just this cluster's members (reusing its `decide()` logic verbatim, not a reimplementation), while a bureau-scoped reviewer — who was never able to decide this from here — gets a real `<Link>` to the Command Center instead of unlinked text. Clicking the Decision Header's "Resolve the blocker" scrolls to and focuses the relevant checklist item (`ref`s + a 2-second highlight ring) via `focusChecklistItem()` in `submission-detail.tsx`.
- **Zone 3 — Compliance details, collapsed** (a `Collapsible` wrapping OMB reportability, OMB reporting mode, risk profile, high-impact risk management, the full NIST AI RMF per-function breakdown, and similar use cases — the same data/logic as before, just no longer always-expanded). Verdict badges (reportability, reporting mode, RMF overall, similar-use-case count) stay visible on the collapsed trigger row; the reasoning underneath each only renders once the reviewer expands it. Unlike Zones 1-2, this zone renders for **every** viewer, not just reviewers — a submitter checking their own submission's status still needs to see OMB reportability/risk profile/RMF the same way they could before this redesign, so the high-impact determination's recommendation+reasons (handled by the checklist for reviewers) also appears here, read-only, for non-reviewers only.

Formal compliance terms keep their exact on-screen wording throughout (per the glossary decision above) and every one of `lib/glossary.ts`'s nine terms now has at least one `GlossaryTerm` tooltip on this page: `crossBureauRationalization`, `ombReportability`, `consolidatedIndividualReporting`, `highImpactDetermination`, `nistAiRmf`, `coveredPartialGap`, `tokenOverlapMatch`, and `advisory`. (`awaitingBureauSignOff` is used elsewhere; this page's existing bureau sign-off line only ever renders once a sign-off exists, so there was no natural "awaiting" copy to attach it to without inventing new text — left for a future pass if that copy is added.)

Visual pass: card surfaces move off a hardcoded `bg-white` onto the shared `bg-card`/`text-card-foreground` tokens (`components/ui/card.tsx`'s Keystone-driven CSS variables, matching the Command Center dashboard's Keystone-era components) so the page follows `.dark` like the rest of the app. 508: still exactly one `<h1>` (the submission title); the page wrapper (`app/submissions/[id]/page.tsx`) now renders inside a `<main>` landmark alongside the existing `<header>`; every new sub-region is a labelled `<section>`/`<h2>` or a native `<button>`-driven `Collapsible` trigger, so focus order follows document order and the "Resolve the blocker" jump target is itself focusable (`tabIndex={-1}` on the checklist `<li>`).

**Update (issue #157):** the "status-badge colors keep the app's existing hardcoded-Tailwind-shade convention" note above no longer holds — `statusBadgeClasses`/`rmfBadgeClass` already routed through `lib/statusTokens.ts` (issue #156), but `REPORTABILITY_CLASSES`, `HIGH_IMPACT_BADGE_CLASS`, `RiskRow`, the RMF/rationalization checklist status classes, the consolidation/similar-use-case badges, and the decision header's disposition badge and blocking-status banner were still hardcoded `green`/`amber`/`red`/`gray`/`purple`/`blue` shades. All now route through `STATUS_BADGE_CLASS`/`STATUS_BORDER_L_CLASS`; see "Keystone DS pass 2" above for the full list.

## 6. AI integration

- The AI assistant uses the Vercel AI SDK with the Anthropic provider. Calls use `generateObject` with zod schemas, so responses are schema-validated and consistent.
- Two main AI surfaces: the per-step submission assistant (vetting and pushback during the wizard) and the Decision Center comparative briefing (`app/admin/compare-actions.ts`).
- Prompts live alongside the server actions that call them. The model is resolved through a `ModelProvider` port: call sites use `getModel()` from `lib/modelProvider.ts` rather than referencing a provider directly. The default adapter (`lib/adapters/default/anthropicProvider.ts`) uses Anthropic, and the model id is overridable via `LAUNCHPAD_MODEL_ID`. To use an agency's approved endpoint, swap the provider in `lib/modelProvider.ts`.
- Requires `ANTHROPIC_API_KEY` in the environment (read by the AI SDK provider).
- Long AI calls (the comparison briefing) can exceed the default serverless timeout. Raise `maxDuration` on the relevant route segment or a server-component `layout.tsx` (Hobby plan max is 60s).

## 7. The submission wizard

- Multi-step guided flow under `app/submit`, orchestrated by a form container that switches on the current step. Since issue #162, the wizard is a fast 5-step **idea** flow, not a full governance form. Step map: 1 submitter info, 2 business problem & opportunity, 3 proposed solution & expected benefits, 4 technical constraints, 5 idea overview (Scout drafts title + summary), 6 review/submit, 7 confirmation.
- Issue #162 removed three things from intake entirely: Strategic Alignment, the heavy Feasibility & Security block (OMB federal AI use case inventory + M-25-21 minimum-practice fields — see §5's "Two-stage lifecycle" and "Vetting-side governance capture" below), and the submitter *self-rating* fields (`severity`, `implementationComplexity`, `userTimeSavings`, `costSavings`) — value and impact are a Scout/reviewer determination, not something a submitter grades on their own idea. Step 4 (Technical Constraints) is deliberately just one free-text field (`dependencies`) — no self-graded feasibility, no OMB/M-25-21 fields. All of the removed fields stay in `FormData` (`lib/steps.ts`) and the OMB export (`lib/ombExport.ts`) still reads them unchanged; they're simply filled in during vetting instead of at intake. `lib/submissionReadiness.ts`'s idea gate (`missing`/`canSubmit`) only checks the light fields that remain; `lib/fieldRegistry.ts` sentinel-numbers (`step: 15/16/17`) the FIELD_REGISTRY entries for the removed fields so the admin Form Configuration panel (`adminFieldGroups` in `lib/steps.ts`, decoupled from the wizard's own `formPhases`) can still toggle them without the wizard's step-based nav/progress-bar logic (`isStepEnabled`) mistakenly keying off them.
- Wizard state lives in `context/form-context.tsx` and is persisted to the browser, namespaced per signed-in user (`lib/draftStorage.ts`'s `scopedDraftKey`, e.g. `aid-form-data:<userId>`) so switching accounts in the same browser never surfaces another user's draft:
  - localStorage: `aid-form-data:<userId>`, `aid-current-step:<userId>`
  - sessionStorage: `aid-session-active:<userId>`
- Resume logic restores in-progress drafts; resume is clamped to editable steps.
- **Conversational-first alternative (issue #169)** — `/submit/conversational` (`components/launchpad/conversational-intake.tsx`) offers the same idea intake as one assistant-led thread instead of a stepped form, gated on a smaller bare-minimum field set. See §5's "Conversational-first idea intake" above for the full design. It's nested under this same `app/submit` layout, so it reads/writes the identical `FormProvider` state — no separate persistence, no separate resume logic.
- **Guided/Form toggle (issue #170)** — both `/submit` and `/submit/conversational` now render `components/launchpad/intake-mode-surface.tsx`, which puts a labeled toggle above whichever of the wizard/conversational thread is active and lets the submitter flip between them at any point with no data loss (same `FormProvider` state either way). The choice persists per signed-in user (`hooks/use-intake-mode-preference.ts`) and defaults new submitters to Guided. See §5's "Guided/Form mode toggle" above for the full design.

## 11. External integrations (existing adapter examples)

- **Notifications** go through the `Notifier` port. Core calls `getNotifier().send(...)` from `lib/notifier.ts`; the default adapter (`lib/adapters/default/slackNotifier.ts`) wraps `lib/slackWebhook.ts`. Swap for Teams/email in `lib/notifier.ts`.
- **System-of-record sync** goes through the `SystemConnector` port. Core calls `getSystemConnector().pushSubmission(...)` from `lib/systemConnector.ts`; the default adapter (`lib/adapters/default/rallyConnector.ts`) wraps `lib/rallyClient.ts`. `lib/systemConnector.ts` branches to `lib/adapters/aiHub/aiHubConnector.ts` when the active tenant's `aiHubExport` feature flag is set (DoC today) — that adapter maps a submission to the OMB schema by reusing `mapSubmissionToOmbRow` (`lib/ombExport.ts`, the same mapping the OMB CSV export uses) so the field mapping is never duplicated, then POSTs the mapped payload to `AI_HUB_ENDPOINT_URL`. There is no live AI Hub endpoint yet, so an unset `AI_HUB_ENDPOINT_URL` makes the adapter no-op safely (log + succeed) — demo tenants and tenants without the flag are unaffected. The Decision Center's Approve action (`components/submissions/submission-detail.tsx`) calls the server action `app/systemConnector-actions.ts`'s `pushApprovedSubmission(...)` — which just calls `getSystemConnector().pushSubmission(...)` — once a submission's status flips to `approved`, so an approved use case is always pushed through whichever connector the tenant resolves to.
- `slackWebhook.ts` and `rallyClient.ts` are placeholders today. The ports mean that when they are wired into the submit/decision flow, core code depends on the interface, not the concrete service.

Seed demo data via the `app/api/seed` route (see `lib/seedSubmissions.ts` for USPTO, `lib/seedSubmissionsDoc.ts` for DoC).

**DoC demo reset:** the admin Demo Data card's "Reset Demo Data" button (`app/admin/page.tsx`) wipes the tenant's `submissions` table (`clearSubmissions()`) and re-triggers `/api/seed`, which re-inserts `docSeedSubmissions` — a deterministic golden state of 12 submissions covering every review status (submitted, in review, needs info, approved, rejected, plus a submitter-owned draft), a near-duplicate comparison pair for the Decision Center, cross-bureau/office coverage, all three OMB reportability outcomes (reportable/excluded/review), a high-impact example with its risk fields populated, and a cross-bureau **consolidated trio** — three independently-worded submissions from NIST, NOAA, and ITA that all match `lib/ombConsolidation.ts`'s `meeting_transcription` category — so the bureau roll-up's "consolidates to N OMB reportable entries" summary actually collapses (12 → 10) instead of reading 1:1 with the submission count. `lib/seedSubmissionsDoc.test.ts` asserts this shape holds against the real `determineReportability`/`findSimilar`/`determineConsolidation` logic, not hand-picked expectations.

`/api/seed` builds each row's `status`/`owner_email`/`business_unit`/`office` workflow columns up front from `form_data` and inserts everything in a single batch, retrying once as a whole batch without `office` if that column doesn't exist yet (pre office-hierarchy migration). This replaced an earlier insert-then-N-per-row-update version: that pattern was slow enough to make "Reset Demo Data" look hung, and a page reload mid-flight could interrupt the update loop and leave some rows stuck on their DB-default `submitted` status — the cause of a live check turning up zero rejected/high-impact/reportable-variety rows despite the seed data having them. The button itself now runs the clear+reseed asynchronously with a spinner and is disabled while in flight, refreshes the shared submissions cache on success instead of reloading the page, and surfaces failures (including a partial clear) via a toast rather than leaving the page looking frozen.

## 14. Where customization is meant to happen (the boundary)

LaunchPad's value is the **core**: the wizard engine, AI vetting logic, readiness/risk scoring, pipeline, and Decision Center.

Everything **agency-specific** — authentication, the AI model endpoint, the database/hosting, outbound connectors to agency systems, branding, and field config — should live in a thin, **swappable integration layer** around that core.

Keeping that boundary clean is both an architecture goal and an **IP-protection goal**: government-funded integration work can happen in the adapter layer without touching the proprietary core. The integration-layer roadmap subtasks track building this out.

The detailed design — the six port interfaces (ModelProvider, SubmissionStore, IdentityProvider, Notifier, SystemConnector, TenantConfig), their default implementations, who-touches-what rules, and migration order — lives in `docs/BOUNDARY.md`.

The repo is licensed **proprietary** (see `LICENSE`): all rights reserved, offered as a commercial item, delivered to government with restricted rights. The core stays Packaged Agile's; only the adapter layer is open to agency or government-funded contribution.

## 15. Gotchas

- Supabase URL trailing slash -> PGRST125 "Invalid path".
